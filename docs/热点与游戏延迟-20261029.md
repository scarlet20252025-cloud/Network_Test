## 一、热点开不起来

### 现场事实（用户机 MARISA\63526，2026-10-29 00:40 实测）

```
GetConnectionProfiles：
  GDPZ-student-5G   LocalAccess   iana=71   ← 当前连着的校园网
  其余 28 个历史 WLAN 配置档  None     iana=71
  FerryTun          InternetAccess iana=53  ← 唯一的「有外网」连接
```

`Get-NetIPAddress`：没有任何 `192.168.137.x`。
`Get-Service SharedAccess`：Running（但停的时候卡在 STOP_PENDING 不动）。

### 三层根因（按发现顺序）

**① 共享源选错（1.0.44 的逻辑在这个场景下必然选错）**

1.0.44 的 `PickShareProfile()` 要求 `level == "InternetAccess" && 物理网卡`。
但渡口的主场景就是「校园网禁网」—— 那时物理网卡只有 `LocalAccess`，
全机唯一的 `InternetAccess` 是 `FerryTun`（TUN 虚拟网卡，iana=53）。

于是：物理网卡选不到 → 落到 FerryTun → 见 ②。

**② FerryTun 当共享源必卡死（1.0.41 的错误，2026-10-29 复现）**

| 共享源 | StartTetheringAsync 结果 | state |
|---|---|---|
| `GDPZ-student-5G`（物理） | `Success` | `On` |
| `FerryTun`（虚拟） | **25 秒超时（THROW:timeout）** | `InTransition` 卡死 |

虚拟网卡当共享源时 ICS 的 NAT 方向无法确定，状态机直接卡住。
这坐实了 1.0.44 的判断（1.0.41 改成 FerryTun 优先是错的），
但 1.0.44 的修法没解决问题 —— 因为它仍然要求 InternetAccess。

**③ 卡死之后不会自愈**

`InTransition` 一旦卡上，后续所有操作全部超时：

```
stop  = timeout(8000)
start = timeout(25000)
换频段（2.4G / Auto / 5G）全部 CFG-THROW + START=THROW:timeout
重启 WlanSvc 无效
```

只有「重启 ICS 服务」能救回来：

```
sc queryex SharedAccess → STOP_PENDING, PID 20528
taskkill /f /pid 20528  → 成功
sc start SharedAccess   → Running
```

### ④ 还有一层：AP 网卡停在 169.254（本次未能突破）

共享源换对（物理网卡）之后：

```
START = Success
state = On
AP 网卡 = 本地连接* 2 (idx=18, Microsoft Wi-Fi Direct Virtual Adapter #2, Up)
AP 网卡 IP = 169.254.154.25/16     ← 60 秒内一直是这个
192.168.137.1 = 始终没出现
netstat 查 67 端口（ICS 的 DHCP 分配器）= 没有任何监听
```

手动 `netsh interface ipv4 set address` 能给 AP 网卡配上 192.168.137.1
（说明网卡本身可控），但 ICS 的 DHCP 没起来，手机连上也拿不到地址。

`Hotspot.cs` 文件头 2026-10-27 就记过这个限制：**SoftAP 驱动状态卡死，
软件层（重启热点、换共享源、重写 SSID、重启网卡）全部无效，只能重启电脑。**

### 已改的代码（1.0.45）

| 改动 | 文件 | 理由 |
|---|---|---|
| 共享源改判「已连接的物理网卡」（`level != None`），不再要求 InternetAccess | `Hotspot.cs` `PickShareProfile()` | 禁网场景下物理网卡永远不是 InternetAccess |
| 排除热点自己的 AP 网卡（按适配器描述含 `Wi-Fi Direct` 判断，不靠名字前缀） | 同上 + 新增 `IsApProfile()` | 热点起来后 AP 网卡会以 `本地连接* N` / SSID 出现在列表里，选它就是自己共享给自己 |
| 虚拟网卡一律不当共享源（宁可报错） | 同上 + 新增 `IsPhysicalProfile()` | FerryTun 必卡死，实测 25 秒超时 |
| `InTransition` 卡死时自动重启 ICS 再试一次 | `Hotspot.cs` `Start()` | 实测能救回来，不必让用户重启电脑 |
| 网卡停在 169.254 时，重启 ICS 后重试一次 Start | 同上 | ICS 半死时 API 照样返回 Success |
| 新增 `RestartIcs()`：`sc stop` → 卡住就 `taskkill /f /pid` → `sc start` | 同上 | `sc stop` 在 STOP_PENDING 上永远等不回来 |

### 待验证 / 待决策

1. **重启电脑后**（清掉 SoftAP 驱动的卡死状态）用 1.0.45 再测一次，
   看 AP 网卡能不能拿到 137.1。这是唯一没验证的一环。
2. **热点客户端能不能上网**：如果共享源是物理 WLAN（校园网禁网），
   ICS 把流量 NAT 到 WLAN 出去 → 客户端没网。
   要真的「共享渡口的网」，共享源必须是 FerryTun，而它必卡死。
   → 这是产品级死结，需要决策：
   - 方案 A：共享源仍用物理网卡，接受「热点能开但客户端没外网」
   - 方案 B：不用 ICS，自己起 SoftAP + DHCP + `New-NetNat` 到 FerryTun
     （参考 `nestchao/Hotspot-Bypass-VPN`，工作量大但能真正共享渡口）
   - 方案 C：热点只用于局域网内互传，明确告诉用户「不共享借网」

## 二、游戏延迟回归（「最新版延迟很高，0.9.30 完全没问题」）

### 结论：不是回归，是 UDP 从「坏的」变成「好的」的副作用

**0.9.30 的 UDP 是坏的**（当时没人发现）：

```powershell
# 0.9.30 的 mihomo-keeper.ps1
$UdpHost = '10.13.24.1'
$UdpPort = 1080        # ← 这是远端 SOCKS5 的 TCP 端口，不收 UDP
```

远端中继按 RFC 1928 实现：UDP 端口不是固定的 1080，而是**每建立一条
TCP ASSOCIATE 才新开一个随机 UDP socket**，端口放在回复的 BND 里。
往 `10.13.24.1:1080` 直接发 UDP 永远收不到回包。

所以 0.9.30 的 TUN 模式下：

```
游戏 UDP → TUN → mihomo → ferry-udp(10.13.24.1:1080) → 没人收 → 静默失败
```

**游戏 UDP 实际是不通的**，游戏要么回落 TCP、要么走别的路 ——
体感就是「延迟没问题」。

**1.0.9 起 UDP 真的通了**（`CHANGELOG v0.14.5`）：

```powershell
# 现在的 mihomo-keeper.ps1
$UdpHost = '127.0.0.1'   # 指向本地代理，由它去和远端协商
$UdpPort = 0             # 渲染时换成探测到的本地 SOCKS 端口
```

完整路径变成：

```
游戏 → TUN(FerryTun) → mihomo → ferry-udp(127.0.0.1:10801)
     → 客户端 ProxyServer → AssociateUpstream(10.13.24.1:1080)
     → 远端 Python 中继 → 游戏服务器
```

延迟 = 本机→pcs（校园网，实测 UDP 往返 6.8ms）+ pcs→游戏服务器（联通出口，
跨网通常 30–80ms）+ 回程。**比直连多绕一大圈，延迟必然高。**

### 用户机当前配置（`%LOCALAPPDATA%\Ferry\config.json`）

```json
"directSocks": true,      // 直连模式 → UDP 上游 = 远端 10.13.24.1:1080（真支持 UDP）
"useTun": true,           // TUN 开着 → 所有 UDP 都被接管
"udpRelayHost": "10.13.24.1", "udpRelayPort": 1080
```

两个条件同时成立，游戏 UDP 才真的绕远端。

### 附带发现：隧道模式下 UDP 是坏的（新 bug）

`FerryRuntime` 里上游只有一个：

```csharp
string upstreamHost = "127.0.0.1";
int upstreamPort = _socksPort;
if (_cfg.DirectSocks) { upstreamHost = _cfg.RemoteHost; upstreamPort = _cfg.RelayPort; }
_proxy = new ProxyServer(_httpPort, upstreamPort, upstreamHost, _log);
```

`DirectSocks = false`（隧道模式）时，UDP 的 `AssociateUpstream` 会连
**本机 ssh -D 的端口** —— 而 OpenSSH 的 `-D` 在协议层面就不实现
UDP ASSOCIATE。所以隧道模式下 UDP 必然失败（静默）。

修复方向：给 `ProxyServer` 单独传一个 UDP 上游（`RemoteHost:RelayPort`），
TCP 走 SSH、UDP 走明文直连远端中继。UDP 本来也不适合走 SSH。

### 待决策：游戏延迟怎么修

| 方案 | 做法 | 代价 |
|---|---|---|
| A | UDP 默认 DIRECT（游戏直连），设置里给「UDP 也走渡口」开关 | 禁网用户的游戏 UDP 连不上（本来也连不上） |
| B | 按目标 IP 分流：国内/教育网 UDP 直连，其余走 ferry-udp | 需要维护段表；禁网场景下国内段也未必通 |
| C | 保持现状，只修隧道模式的 UDP 上游 bug | 直连模式下延迟仍然高 |

**需要用户确认的场景**（否则只能猜）：
- 反馈者打的是什么游戏？
- 当时校园网是「能上网」还是「被禁网」？
- 延迟数值大概多少（直连 vs 走渡口）？
- 有没有开 TUN？

## 二之二、🚨 真实事故：在用户机上开热点，把他的 WiFi 顶掉了

**经过**：为了验证 1.0.45 的共享源修复，我在用户自己的机器上直接调
`StartTetheringAsync()`。结果 **Realtek 8852BE 的 STA 连接被顶掉** ——
他正在用的 WiFi 断了，远控同时失去，他没法再给我指令，只能等它自己恢复。

**这不是「运气不好」，是单网卡的物理限制**：

单块无线网卡做 SoftAP 时，STA 和 AP 共用同一套射频前端。
很多驱动（含 8852BE）接到 SoftAP 请求后**不是拒绝，而是切换射频配置** ——
表现就是「AP 起来了、STA 掉了」。

| 场景 | 能否同时 | 说明 |
|---|---|---|
| 有线网卡上行 + WiFi 做 AP | ✅ | 两个独立硬件 |
| 两块 WiFi（一块 STA、一块 AP） | ✅ | 同上 |
| **单块 WiFi 同时 STA + AP** | ❌ | 多数驱动做不到，失败方式是「顶掉 STA」 |

**为什么系统设置 UI 是安全的、直接调 API 是危险的**：

> 用户分享的《开启移动热点的操作方法》里，方法一（系统设置 UI）是安全的 ——
> **UI 会先做能力检查，不支持就不让你开**；
> 而直接调 WinRT API 是**强行下命令**，驱动就靠「踢掉 STA」来满足它。

**由此产出的代码改动（1.0.45）**：

- 新增 `Hotspot.UplinkRisk()`：判定「共享源是无线网卡，且它是本机唯一上行」
  → 返回警告文案。
- `MainWindow.OnHotspotToggled()` 在开热点**之前**弹确认框，
  明确写「你现在的 WiFi 会断（这台机器可能就此失去远程连接）」，
  用户点「否」就不开。
- 只有「有线做上行」或「有第二块已连接的网卡」时才不打扰。

**由此产出的操作规则（写进 `AGENTS.md` 最高优先级一节）**：

1. **禁止**在用户正在使用的机器上调用 `StartTetheringAsync` /
   `StopTetheringAsync` / `ConfigureAccessPointAsync`，也禁止重启 `WlanSvc` /
   停 `SharedAccess` / 禁用启用无线网卡。
2. 热点的写操作只在两种前提下做：去 **10.113.66.6** 测试机，
   或用户**当次明确说**「我现在不用网，你随便弄」。
3. 授权按次算，不按任务算。**动手前问一句。**
4. 只读诊断（`Get-NetAdapter` / `Get-NetIPAddress` / `Get-Service` / 读日志）不受限：
   **读随便读，写先问。**

**这也基本解答了「热点到底能不能做」**：如果上行就是那块 WiFi，
再拿它做 AP 必然二选一。这类机器上正确做法是**明确拒绝并说明原因**，
而不是硬开把用户的网断掉。
