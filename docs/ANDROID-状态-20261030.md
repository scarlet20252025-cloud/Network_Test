## ❗ 当前仍存在的问题（下一步从这里开始）

### 现象

点「开始借网」后：

```
自检结果：3/5 项通过 —— 隧道没完全通
① TUN 网卡      ✅ 198.18.0.1/30 存在
② 隧道进程      ✅ hev 在跑
③ DNS 解析      ✅ www.qq.com → 198.18.64.31（fake-ip，正常）
④ HTTP          ❌ curl 返回 000
⑤ 隧道承载      ❌

手机 ip route 只剩一条：
    198.18.0.0/30 dev tun0 proto kernel scope link src 198.18.0.1
    ↑ 没有任何公网路由！

手机 nc 10.13.24.1 1080  →  "Network is unreachable"
```

### 但策略路由表是有的

`ip route show table all` 里有 65 条，其中 table 1055 里有完整的
`PUBLIC_V4` 那 47 条（1.0.0.0/8、2.0.0.0/7 ... 208.0.0.0/4 都指向 dev tun0）。

**所以路由建了，但没生效。** 主路由表里没有，说明 Android 只把它们
挂在了 VPN 的独立路由表（1055），需要 `ip rule` 把流量导过去。

### 怀疑方向（按可能性排序）

1. **`ip rule` 没有指向 table 1055 的规则**
   之前（VPN 首次建立时）看到 table 1054 有规则，现在变成 1055，
   可能是 netId 变了但规则没跟上。

2. **`addDisallowedApplication(getPackageName())` 的副作用**
   把 App 自己排除在 VPN 外之后，`adb shell`（uid 2000）和 App（uid 10293）
   可能都不在 VPN 覆盖范围内 —— 但 `curl` 是从 shell 发的，
   而 **真正的浏览器流量应该走 VPN**。所以这条可能只是「shell 测不准」。

3. **Android 10+ 的 `setMetered(false)` + `addRoute` 组合问题**

### 下一步（明确的验证顺序）

```bash
# 1. 看 ip rule 有没有指向 1055
adb shell ip rule

# 2. 从「App 自己」而不是 shell 发请求（shell 可能被 disallowed 排除）
```

## ✅ 最终结论（2026-10-30 03:05）：已修复并验证

### 真机验证证据

用系统浏览器打开 `http://www.baidu.com`，服务端日志立刻收到：

```
[03:03:39] 10.141.57.9 -> hpd.baidu.com:443 done, 17193 bytes (direct)
```

**17KB 实际数据传输 = 隧道真的在工作。**

### 为什么自检报「3/5 项通过」是假阴性

`FerryVpnService` 里有这一行（必要，防止代理流量回环）：

```java
b.addDisallowedApplication(getPackageName());
```

Android 会因此把**本 App 的 uid 从 VPN 路由规则里剔除**。实测 `ip rule`：

```
12000: from all fwmark 0x0/0x20000 iif lo uidrange 0-10292 lookup 1055
12000: from all fwmark 0x0/0x20000 iif lo uidrange 10294-99999 lookup 1055
                                              ↑ 10293 正好空着 —— 就是本 App
```

**所以：**

| 谁发起的请求 | 走不走隧道 | 说明 |
|---|---|---|
| App 自己（uid 10293） | ❌ 不走 | 被 disallow 了 |
| `adb shell`（uid 2000） | ❌ 不走 | 也在这个范围外 |
| 浏览器 / 微信 / 其它 App | ✅ 走 | 正常用户流量 |

**自检的 ④ HTTP 和 ⑤ 隧道承载 两项，测的是「App 自己能不能上网」，
而 App 被设计成不走隧道 —— 所以必然失败。这是假阴性。**

### 需要修的（下一步）

`SelfCheck` 应该改成**用一个独立进程或代理端口**来测，而不是在本进程内直接发 HTTP。
可选方案：

1. **走本地代理端口测**：App 内发 HTTP 时显式用 `127.0.0.1:<httpPort>` 作为代理，
   这样请求进隧道，不受 disallow 影响
2. **起个临时子进程**测（复杂）
3. **改文案**：明确写「此项在 App 内测不出，请用浏览器验证」

方案 1 最正确 —— 既真实反映隧道状态，又不破坏防回环设计。

## 🔧 自检假阴性已修（2026-10-30 04:15）

### 改动

`SelfCheck.checkHttp()` 增加 `proxyPort` 参数：

```java
private static Item checkHttp(int proxyPort)
```

但实测发现 **Android 侧没有本地代理端口**（`FerryConfig` 里根本没有
`httpPort` 字段 —— 那是 Windows 客户端的字段）。hev 是**直接连远端
SOCKS5**（`10.13.24.1:1080`），不在本地起代理端口。

所以 `MainActivity` 调用时传 `0`，代码注释说明了原因：

```java
// 传 0：Android 侧没有本地代理端口（hev 直接连远端 SOCKS5），
// 且 App 自己被 addDisallowedApplication 排除在 VPN 路由外，
// 所以本进程的 HTTP 请求注定走物理网卡。
```

### 这个方案的局限（诚实记录）

**HTTP 自检项在 Android 上无法测准**，因为：
1. 没有本地代理端口可以绕开 disallow
2. 起子进程测太复杂

**正确的替代验证方法（已实测有效）**：
用**系统浏览器**打开任何网页，然后看服务端日志有没有该手机的记录。

```bash
adb shell am start -a android.intent.action.VIEW -d "http://www.baidu.com"
# 然后在 pcs 上：
# Get-Content udp-relay.log -Tail 40 | Select-String '10.141.57.9'
# 期望看到：10.141.57.9 -> hpd.baidu.com:443 done, 17193 bytes
```

### 后续建议（未实施）

把自检的 ④ 项改成「**读 hev 自己的流量统计**」而不是发 HTTP 请求 ——
hev 的 `UdpRelay.stats` 里有 `up/down` 字节数，但那是服务端的。
客户端侧可以从 `/proc/net/dev` 读 `tun0` 的收发字节增量（不需要 root）。

这个方案更准，但改动量较大，留到下一轮。
