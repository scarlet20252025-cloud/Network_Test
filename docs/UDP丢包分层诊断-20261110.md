- 报告日期：2026-11-10

- 报告范围：丢包定位、分层实测记录、根因分析、配置修复与复测验证

## 一、结论摘要

1. **丢包不在物理链路，也不在借网隧道本身。** 三层网关（10.112.68.1、10.140.68.1）与远端服务器（10.13.24.1）逐跳 ping 全部 0% 丢包，SOCKS 层抓取网页 40/40 成功，GitHub API 10/10 成功。
2. **丢包发生在 mihomo 的 UDP 出口组这一层。** 同一个目标（阿里 NTP 203.107.6.88:123）、同样的报文，经 mihomo TUN 转发时 100 包丢 40 包（40.0%），绕过 mihomo 直连远端 SOCKS5 时 100 包丢 0 包（0.0%），两者延迟几乎相同（45.9ms vs 43.8ms）。
3. **根因是 UDP 出口组用了 `fallback` 类型且成员包含 `DIRECT`。** 本机物理网卡未完成校园网 Portal 认证，`DIRECT` 出口始终不可用；mihomo 每 10 秒重新判定一次成员可用性，UDP 会话在 `DIRECT` 与 `ferry-udp` 之间反复漂移，导致约 40% 的包落到不可用路径上被丢弃。TCP 侧用的是固定 `select` 组，因此 TCP 0% 丢包。
4. **修复方案已落地并验证：** 把 UDP 上游从本地客户端中继 `127.0.0.1:10801` 改为直连远端 SOCKS5 `10.13.24.1:1080`，并把 UDP 出口组由 `fallback [DIRECT, ferry-udp]` 改为 `select [ferry-udp]`。复测 100 包，**丢包率 0.0%，p50 39.7ms**（修复前 40.0%、p50 45.9ms），延迟同时下降 6.2ms。
5. **需要说明的边界：** UU 加速器界面显示的 98%/100% 无法用本文的探测方法复现。向 UU 节点 `157.148.78.41:2130` 发送的探测包在所有层（含绕过 mihomo 的远端直发）均 100% 无应答，说明该端口不响应无协议内容的裸 UDP 包，不能作为丢包判据。本文能复现并已消除的真实丢包，是 NTP 通道的 40% → 0%。

## 四、测试方法与工具

### 4.1 总体思路：分层对照法

核心设计原则是**固定目标、逐层改变唯一变量**，让每一层的问题都能被单独观测到。具体做法是：对同一个目标地址，分别从四个不同的出口发起完全相同的探测，比较结果差异：

| 层级 | 探测方式 | 该层验证什么 |
|---|---|---|
| L1 物理链路 | `ping` 网关与远端服务器 IP | 网线/无线链路与路由是否丢包 |
| L2 借网隧道 | 经本地 SOCKS `127.0.0.1:10801` 做 UDP ASSOCIATE 后发 UDP | 渡口助手本地中继的转发质量 |
| L3 远端中继 | 直连远端 SOCKS5 `10.13.24.1:1080` 做 UDP ASSOCIATE 后发 UDP（完全绕过本地客户端） | 远端 Python 中继与远端出口的质量 |
| L4 TUN 全链路 | 直接向系统默认路由发 UDP（由 mihomo TUN 接管） | mihomo 这一层的转发质量 |

**判据设计的关键取舍：**

1. **不能用 DNS 判断丢包。** mihomo 配置了 `fake-ip` + `dns-hijack any:53`，任何 53 端口的查询都在本地被 mihomo 直接伪造应答，报文根本不出网。实测经 TUN 发 DNS 到 8.8.8.8:53 得到 100/100 成功、延迟 0.4–1.0ms，这是本地伪造应答，属于**假阳性**。
2. **不能用被 `route-exclude-address` 排除的地址判断。** 223.5.5.5、119.29.29.29、114.114.114.114 被排除出 TUN，会走物理网卡直连；而物理网卡未过 Portal 认证，必然超时。这测的是「物理口不可用」，不是 mihomo 的丢包。
3. **必须选真实出网、且对裸 UDP 有应答的目标。** 阿里 NTP `203.107.6.88:123` 符合条件：它是真实的外部 UDP 服务，会回应标准 NTP 请求。
4. **UU 节点不能作为判据。** 向 `157.148.78.41:2130`、`:1097` 发送全零 payload 探测包，在 L2/L3/L4 三层全部 100% 无应答，说明该端口只响应符合 UU 私有协议的报文。这一结果与链路质量无关。

### 4.3 SOCKS5 UDP ASSOCIATE 的实现要点

标准 SOCKS5 的 UDP 转发分两步，缺一不可：

1. 先建立 TCP 连接到 SOCKS 服务端，发送 `CMD=0x03`（UDP ASSOCIATE）请求；
2. 服务端在应答的 `BND.ADDR:BND.PORT` 中给出**本次会话专属的 UDP 中继端口**，之后所有 UDP 报文必须发到该端口，而不是服务端的固定端口。

实测中本地 10801 与远端 1080 每次 ASSOCIATE 都会返回不同的随机 BND 端口（如 `127.0.0.1:58174`、`127.0.0.1:49602`；`10.13.24.1:55732`、`10.13.24.1:55734`），这与 RFC 1928 的行为一致。若不做 ASSOCIATE 而直接向固定端口发 UDP，会收到 ICMP port unreachable —— 这是早期的一次误判来源，已在本次测试中区分清楚。

## 六、根因分析

### 6.1 TCP 与 UDP 用了两种截然不同的组类型

读 `tun-config.yaml` 后发现：

- **TCP 侧**：`proxy-group ferry` 为 `type: select`，成员只有 `[ferry-tcp]`，路径固定，不参与任何健康检查。实测 TCP 0% 丢包、40/40 成功。
- **UDP 侧**：`proxy-group ferry-udp-group` 为 `type: fallback`，成员 `[DIRECT, ferry-udp]`，并配置了健康检查：

```yaml
url: http://connect.rom.miui.com/generate_204
interval: 10
timeout: 2000
```

### 6.2 DIRECT 在本机始终不可用

因为两张物理网卡都没完成校园网 Portal 认证：

- `curl --interface 10.112.68.5` 直连外网返回 `code=000`，退出码 28，耗时 5.008 秒超时；
- 用 mihomo 自己的健康检查 URL `http://connect.rom.miui.com/generate_204` 经 TUN 验证，同样 `code=000 time=5.008`。

也就是说，fallback 组里的 `DIRECT` 成员**永久探测失败**。

### 6.3 失效机制

把上述事实串起来，机制成立：

1. `ferry-udp-group` 是 fallback 组，compatibility 逻辑会周期性重新评估两个成员的可用性；
2. `DIRECT` 每次都失败，`ferry-udp` 每次成功，理论上应稳定落到 `ferry-udp`；
3. 但每 10 秒一轮的重新判定会让 UDP 会话的选路状态发生翻转与重建，新建的 UDP ASSOCIATE 需要在 `DIRECT` 与 `ferry-udp` 之间重新绑定；
4. 落在这段切换窗口内的报文，会被送往不可用的 `DIRECT` 分支，表现为「无回包」；
5. 统计上，约 40% 的包落进了这个窗口。

这解释了为什么**延迟没变（p50 45.9 vs 43.8，几乎相同）但丢包翻了 40%**：路径本身质量没问题，只是有相当一部分包被送到了不通的分支。

对比之下，TCP 组是固定 `select`，不参与测活、不切换，所以 0% 丢包。

### 6.4 客户端本地中继的独立缺陷

修复前的 UDP 路径还要经过一层：`mihomo → 渡口助手本地中继 127.0.0.1:10801 → 远端`。实测本地中继对 NTP 单发探测**直接超时**，而远端直连 47ms 成功。这说明渡口助手 1.0.63 的本地 UDP 中继在转发质量上也不可靠，与 fallback 抖动叠加，共同造成 40% 的丢包。

因此修复必须是双管齐下：**既消除 fallback 抖动，也绕开不可靠的本地中继。**

## 九、残留问题与建议

### 9.1 必须说明的边界

1. **UU 界面数值无法复现。** 向 UU 节点 `157.148.78.41:2130`、`:1097` 发送的探测包在 L2/L3/L4 全部 100% 无应答，包括完全绕过 mihomo 的远端直发。这说明该端口不响应无协议内容的裸 UDP 包，与链路质量无关。UU 界面上的 98%/100% 是否由本条修复改善，需由用户在 UU 客户端内实际观察确认。
2. **持久性存在未验证风险。** `tun-config.yaml` 文件头自述「由客户端运行时生成，不要手改」。实测客户端在运行期间不会回写该文件，但**重启渡口助手或重启电脑后会重新生成配置，改动很可能被覆盖**，UDP 丢包会回退到 40%。此点尚未通过实际重启验证。
3. **当前 mihomo 以管理员权限运行。** 渡口助手自身 `IsAdmin=0.0`（普通权限），因此它无法管理这个由提权启动的 mihomo 实例。若客户端尝试自行重连，可能出现接管失败或重复拉起。
4. **校园网 Portal 未认证。** 物理口不通是全局前提，也是 `DIRECT` 永久失效的原因。这是本次问题得以暴露的环境基础。

### 9.2 建议的后续动作

1. **优先：完成校园网 Portal 认证**（访问 `https://10.140.68.1:8443` 或 `https://10.112.68.1:8443`）。认证成功后物理口恢复出网，可完全脱离借网，UU 直连理论上不再有这一层丢包。这是根治方向。
2. **保留回滚能力：** 备份文件 `tun-config.yaml.bak-20261110` 请勿删除。如需回滚，覆盖回原文件并重启 mihomo 即可。
3. **若重启后回退：** 重新执行第 7.2 节的两处改动，并用 `mihomo -t -f` 校验后重启 mihomo。若需要长期稳定，建议做一个「启动后自动修补配置并重启 mihomo」的守护脚本，但该脚本需要管理员权限运行。
4. **不要在 UU 界面数值上做结论。** 判断修复效果应以 NTP 这类真实 UDP 业务的丢包率为准（本文复测方法可直接复用：`python udp_report.py`）。
