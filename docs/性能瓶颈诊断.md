# 性能瓶颈诊断报告

采样时间：2026-10-23 03:30–04:00
环境：远端 `pcs` = 10.13.24.1（Xeon E-2244G 8 核 / Realtek 千兆网卡 / Win10 19045）

---

## ⚠️ 重要更正

**本报告第一版结论「远端带宽上限 1 MB/s」是错的。**

错因：只用清华源（`mirrors.tuna.tsinghua.edu.cn`）单一下载源做测速。
清华源在 CERNET，远端办公网到 CERNET 的路由很差 → 实测只有 1 MB/s。
换华为云源后同一台机器实测 **90+ MB/s**。

**教训：测带宽必须多源交叉，单一源测出的可能是「到某个源的路由质量」，不是带宽上限。**

**华为云 89 MB/s vs 清华 1.12 MB/s，差 80 倍 —— 同一台机器、同一时刻。**

### 1.2 网卡实时速率（华为云下载中采样）

```
第1秒: 85.33 MB/s
第2秒: 88.88 MB/s
第3秒: 91.47 MB/s

```

**稳定 90 MB/s 左右 = 720 Mbps**，千兆网卡跑到 72%，属于正常水平。

### 1.3 多源并行（验证是否还有余量）

3 个不同源同时下载合计 **1.09 MB/s** —— 这个数字低是因为其中两个源（清华、阿里）
本身就是慢的，只有华为云在真正出力。不能据此判断总出口上限。

### 1.4 经借网 vs 直连（本机视角，华为云源）

| 路径 | 速度 |
|---|---|
| 借网 HTTP 代理（10809） | **36.47 MB/s** |
| 借网 SOCKS5（10808） | 20.37 MB/s |
| 本机直连 | 7.80 MB/s |

**借网比直连快 4.7 倍。** 这说明：
1. 远端出口带宽充裕，SSH 隧道不是瓶颈；
2. 本机自己的网络反而更差；
3. HTTP 代理模式比 SOCKS5 模式快近一倍（dual-proxy 的 CONNECT 复用 + 首字节分流更高效）。

## 五、系统代理事故与修复

### 5.1 事故现象

用户报「开启借网之后，浏览器都不能访问了」。

### 5.2 根因

`borrow-net.ps1` 里有一段回退逻辑：

```powershell
$sysProxy = "127.0.0.1:$SocksPort"                    # ← 10808 是 SOCKS5 端口
if ($bridgeOk) { $sysProxy = "http://127.0.0.1:$HttpPort" }
Set-ItemProperty $k -Name ProxyServer -Value $sysProxy
```

当 `dual-proxy.mjs` 没起来（`$bridgeOk = $false`）时，它把系统代理写成
`127.0.0.1:10808` —— **那是纯 SOCKS5 端口**。

**Windows 系统代理（WinINET `ProxyServer`）只支持 HTTP 代理。**
所有读系统代理的程序（浏览器 / .NET / Electron / git for Windows）
会把 SOCKS5 端口当 HTTP 代理去连 → 全部秒失败。

实测证据：
```
ProxyServer = 127.0.0.1:10808
[System.Net.WebRequest]::GetSystemWebProxy().GetProxy(baidu) = http://127.0.0.1:10808/
Invoke-WebRequest https://www.baidu.com → An error occurred while sending the request.
```

### 5.3 修复

**硬性保护：HTTP 代理没起来时，绝对不写系统代理。**

```powershell
if (-not $bridgeOk) {
  Write-Host "  ❌ HTTP 代理 $HttpPort 未就绪，已跳过系统代理切换" -ForegroundColor Red
  Write-Host "     （不写 SOCKS 端口：系统代理只认 HTTP，写 SOCKS 会让浏览器全部打不开）"
  Write-Host "     隧道本身可用：应用可自行配 SOCKS5 127.0.0.1:$SocksPort"
  return
}
...
$sysProxy = "http://127.0.0.1:$HttpPort"
```

修完验证：
```
ProxyServer = http://127.0.0.1:10809
.NET Invoke-WebRequest baidu    → 200
.NET Invoke-WebRequest github   → 200
.NET Invoke-WebRequest qq       → 200
```

## 六、可尝试的优化（按收益排序）

### 6.1 ⭐ 让 dual-proxy 常驻并优先使用 HTTP 代理

实测 HTTP 代理 36.47 MB/s vs SOCKS5 20.37 MB/s，**差近一倍**。
系统代理应始终指向 `http://127.0.0.1:10809`（现已如此）。

### 6.2 ⭐ smart-resolve 池按实时探测重排

`140.82.121.4` 在池里排第 1 但实测 0/2，逐个试会先浪费一次 6s 超时。
建议加一个后台定时探测（每 30 分钟），把实测通过的 IP 提到最前。

### 6.3 下载大文件时选对源

同一台远端：
- 华为云 89 MB/s
- 清华 1.12 MB/s

**差 80 倍。** 办公网到 CERNET 路由差，到华为云/阿里云（BGP）好。
大文件优先用华为云、阿里云镜像。

### 6.4 DNS 顺序微调

`10.10.1.9`（avg 12ms）排在 `10.10.1.10`（avg 1ms）后面或去掉。收益个位数 ms。

### 6.5 不可行的方向（已排除）

| 方案 | 为什么不行 |
|---|---|
| 加并发线程提升总带宽 | 华为云单线程已 89 MB/s，4 线程反而降到 74.93（源侧限速） |
| 换 DNS 改善 github | 8 个渠道返回同一 IP |
| 调 TCP 窗口 | 已是 normal + CUBIC，90 MB/s 说明窗口充足 |
| 用 WireGuard 替代 SSH | SSH 隧道实测 36 MB/s，不是瓶颈；WG 从未握手 |
| 走 IPv6 | 远端无 IPv6 地址 |
| 关闭「节能以太网」 | 持续下载 90 MB/s，该策略未实际限速 |

## 七、最终判定

**远端出口带宽 90+ MB/s（≈720 Mbps），经借网可跑 36 MB/s，链路健康。**

第一版报告的「1 MB/s 硬上限」结论**作废** —— 那是清华源路由问题。

真正需要关注的不再是带宽，而是：
1. **github 可达性**（DNS 返回的 IP 不可达，靠 smart-resolve 择优解决）；
2. **系统代理协议匹配**（只能写 HTTP 端口，不能写 SOCKS5 端口 —— 已加硬保护）；
3. **下载源选择**（同一台机器不同源差 80 倍）。

当前 36 MB/s 对任何日常用途都绰绰有余。
