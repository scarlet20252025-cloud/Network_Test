## 一、物理链路排查（全部排除）

```

wg0     100 Gbps  WireGuard Tunnel（虚拟，非真实带宽）
PCIe LinkSpeed 2.5 GT/s x1 → 约 250 MB/s，远高于 1 MB/s 需求
```

**高级属性里有一条需要注意**：

## 二、带宽瓶颈定位（关键实验）

用清华源 Ubuntu ISO 做并发下载测试（每档 8 秒）：

| 并发数 | 合计吞吐 |
|---|---|
| 1 | **1.02 MB/s** |
| 2 | 1.05 MB/s |
| 4 | 1.03 MB/s |
| 8 | 0.92 MB/s |

### 判定逻辑

单 TCP 连接吞吐上限 ≈ `窗口 / RTT`。
- 若**多连接 >> 单连接** → 瓶颈是窗口（可优化）
- 若**多连接 ≈ 单连接** → 瓶颈是物理带宽（不可优化）

实测并发 8 反而略降（0.92）。**结论：瓶颈是远端出口的物理带宽上限，不是 TCP 窗口。**

### 旁证

远端自身直下清华源：**0.95 MB/s**
本机经 SSH 借网：**1.05 MB/s**

借网甚至比远端自己略快（SSH 有压缩？实际是采样波动）。**SSH 隧道零带宽损耗。**

## 三、DNS 排查

### 3.1 各 DNS 服务器响应速度（5 个域名 × 3 次）

| DNS 服务器 | 成功 | 失败 | p50 | avg |
|---|---|---|---|---|
| 10.10.1.9 | 15 | 0 | 1ms | 12ms |
| **10.10.1.10** | 15 | 0 | **1ms** | **1ms** |
| 192.168.100.1 | 15 | 0 | 7ms | 6ms |
| 223.5.5.5 | 15 | 0 | 7ms | 7ms |
| 119.29.29.29 | 15 | 0 | 7ms | 7ms |

**`10.10.1.10` 最快（avg 1ms）**，是内网 DNS，已经排在列表首位。

### 3.2 github.com 解析结果对比（决定性）

| DNS 服务器 | 返回 IP |
|---|---|
| 10.10.1.9 | 20.205.243.166 |
| 10.10.1.10 | 20.205.243.166 |
| 192.168.100.1 | 20.205.243.166 |
| 223.5.5.5 | 20.205.243.166 |
| 119.29.29.29 | 20.205.243.166 |
| DoH 223.5.5.5 | 20.205.243.166 |
| DoH doh.pub | 20.205.243.166 |
| DoH cloudflare | 失败 |

**8 个渠道全部返回同一 IP**。这是 GitHub 官方权威 DNS 的真实记录，不是污染。
→ **换 DNS 无法改善 github 可达性。**

### 3.3 但 DNS 本身有优化空间

`10.10.1.9` 的 avg 12ms 明显慢于 `10.10.1.10` 的 1ms（虽然 p50 都是 1ms）。
说明 `10.10.1.9` 偶发慢查询，**把它从列表里去掉或调后**可能有微小收益。

## 五、可尝试的优化（按收益排序）

### 5.1 ⭐ 关闭「节能以太网」

```
节能以太网和关闭链路速度 = 10 Mbps 兼容
```

这条策略会在空闲时把链路降到 10 Mbps。**实测带宽 8 Mbps 低于该阈值，有被卡住的嫌疑。**

```powershell
# 远端执行（需管理员）
$eth = Get-NetAdapter -Name '*以太网*'
Set-NetAdapterAdvancedProperty -Name $eth.Name -DisplayName '节能以太网和关闭链路速度' -DisplayValue '已禁用'
# 或找 RegistryKeyword
Get-NetAdapterAdvancedProperty -Name $eth.Name | Where-Object { $_.DisplayName -match '节能' }
```

**这是唯一还有希望的软件层优化。** 建议实测前后对比。

### 5.2 检查是否有 QoS / 组策略限速

```powershell
# 查 QoS 策略
Get-NetQosPolicy -EA SilentlyContinue
# 查组策略里的限制
Get-ItemProperty 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\Psched' -EA SilentlyContinue
```

办公网很可能在交换机/路由器侧做了限速，Windows 侧看不到。

### 5.3 DNS 顺序微调

把 `10.10.1.9`（avg 12ms）从 `10.10.1.10`（avg 1ms）之后调开，或直接去掉。
收益很小（个位数 ms），但零风险。

### 5.4 不可行的方向（已排除，别浪费时间）

| 方案 | 为什么不行 |
|---|---|
| 加并发线程 | 实测 8 线程反而更慢 |
| 换 DNS | 8 个渠道返回同一 IP |
| 调 TCP 窗口 | 已经是 normal + CUBIC，且瓶颈不在窗口 |
| 用 WireGuard 替代 SSH | WG 从未握手，且 SSH 实测零带宽损耗 |
| 走 IPv6 | 远端无 IPv6 地址 |

## 六、最终判定

**远端办公网出口带宽 ≈ 1 MB/s（8 Mbps）是硬上限，软件层无法突破。**

若需更高带宽，只能：
1. 找办公网管理员放开限速（最直接）
2. 换一个出口带宽更大的远端主机
3. 多出口分流（多台远端同时提供 SOCKS，本机做负载均衡）—— 工程量大但可行

当前 1 MB/s 对日常浏览、GitHub 操作、代码拉取是够用的；
看视频、下大文件不行。
