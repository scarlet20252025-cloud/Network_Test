# 出口旁路：借网自动借用远端的 Clash

> 目标：**让借网用户也能上外网，而且不需要做任何设置**。
>
> 实现：中继里加「直连 vs 本机 Clash」的并发竞速。一个文件、一处逻辑。

---

## 一、为什么需要它

远端 pcs 上跑着 Clash（7890），它自己能出去。
但中继原来只把流量**直连**到目标，所以借网用户还是上不了 google。

```
改之前：借网用户 → 中继:1080 → 直连目标（墙外站全部超时）
改之后：借网用户 → 中继:1080 ─┬→ 直连目标        （国内站）
                              └→ 本机 Clash:7890 （墙外站）
```

---

## 二、为什么是「竞速」而不是「按 IP 判断国内外」

维护一份国内外 IP 表不现实（几千条、天天变），而且判断错会让国内站
**更慢**（白白绕一圈到国外）。

先做了三路实测：

| 目标 | 直连 | 中继 | Clash |
|---|---|---|---|
| www.google.com | ✗ | ✗ | ✓ |
| www.youtube.com | ✗ | ✗ | ✓ |
| github.com | ✗ | ✓ | ✓ |
| www.baidu.com | ✓ | ✓ | ✓ |
| api.deepseek.com | ✓ | ✓ | ✓ |

结论：**直连能通的，Clash 也通；直连不通的，只有 Clash 通。**

所以「竞速」既不需要 IP 表，又不会让国内站变慢 ——
谁先连上就用谁，输的那条立刻取消。

---

## 三、为什么给直连一个优先窗口

纯竞速时 Clash 会抢走**国内站** —— 它的本地握手几乎是瞬时的。
实测 baidu 被路由到国外再回来：又慢、又浪费机场流量。

所以：**直连在 0.20 秒内连上就直接用它**（取消 Clash）；
超过窗口才接受 Clash 的结果。国内站实测 100ms 内建连，稳赢。

## 四、三个超时参数（都是实测调出来的）

```
CLASH_FALLBACK_TIMEOUT = 0.9    direct 尝试的超时
DIRECT_HEAD_START     = 0.20    direct 独享的窗口
CLASH_TCP_TIMEOUT     = 0.8    连本机 Clash 的 TCP 超时
CLASH_HANDSHAKE_TIMEOUT = 2.0  等 SOCKS5 握手回复
CLASH_CONNECT_TIMEOUT = 8.0    等 Clash 真正连到目标
DIRECT_ONLY_TIMEOUT   = 3.0    关闭旁路时的纯直连超时
```

### 为什么 `CLASH_TCP_TIMEOUT` 只要 0.8 秒

**这是三个 bug 里最隐蔽的一个**，插桩日志量出来的：

```
[T] phase1 done at 0.213            ← head start 0.20s
[T] race event at 0.913: ['direct'] ← direct 0.9s 超时
[T] race event at 2.010: ['clash']  ← Clash 2.0s 才失败！
```

Clash 端口**没人监听**，本该立刻 connection refused，
实际却等满了超时。原因是 **Windows 上连本机关闭端口不立刻回 RST**，
会重试 SYN 直到超时。

所以 `CLASH_TCP_TIMEOUT` 的值**直接等于失败耗时** —— 必须给小。
回环要么 <5ms 成功，要么就是死的，0.8 秒已经是 160 倍余量。

### 为什么握手超时和 CONNECT 超时要分开

原来两者共用 8 秒，结果 Clash 假死时卡满 8 秒。
这两段性质完全不同：

| 阶段 | 耗时 | 超时 |
|---|---|---|
| 连本机 + SOCKS5 握手 | 纯回环，毫秒级 | 2.0s |
| 发 CONNECT 等响应 | Clash 要真的连目标，慢节点几秒 | 8.0s |

## 五、实测数据

### 正常情况（生产 1080）

| 目标 | 结果 | 走的哪条 |
|---|---|---|
| www.google.com | 200 / 0.574s | clash |
| www.youtube.com | 200 / 0.578s | clash |
| github.com | 200 / 0.808s | direct |
| www.baidu.com | 200 / 0.154s | direct |
| www.bilibili.com | 200 / 0.223s | direct |

### 故障模式（修 bug 前后对比）

| 场景 | 改前 | 改后 |
|---|---|---|
| A. Clash 端口死 | 2.02s | **0.92s** |
| B. Clash 假死 | 8.04s | **2.02s** |
| C. Clash 拒绝 | 1.21s | 0.91s |
| D. Clash 慢 3s | 3.00s | 2.01s |
| E. 正常 | 0.37s | 0.22s |
| F. 关闭旁路 | 10.01s | **3.02s** |

失败时统一返回 SOCKS5 `REP=5`（connection refused），
客户端能正确显示「连接被拒」，不会无限等待。

## 六、配置

`--clash-proxy auto`（默认）自动探测这些端口：

| 端口 | 来源 |
|---|---|
| 7890 | Clash for Windows / mihomo 默认 mixed-port |
| 7891 | Clash 默认 socks-port |
| 7897 | Clash Verge Rev 默认 |
| 10808 | 部分自定义配置 |

探不到就**静默关闭**，不影响正常借网（用户可能没装 Clash）。
`--clash-proxy off` 显式关闭，`--clash-proxy host:port` 手动指定。

---

## 七、对用户完全透明

- 客户端不用改，界面上没有任何新选项或提示
- 日志里只有中继侧两行：
  - `outbound bypass: race to 127.0.0.1:7890 when direct fails`
  - `direct failed, auto-routing via local Clash (e.g. ...)`
- 每条连接结束时带出口标记：`... done, 591006 bytes (clash)`

用户感觉就是「能上外网了」，不知道背后换了出口。
