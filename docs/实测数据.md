## 二、带宽（2026-10-23，多源交叉）

**关键教训：测带宽必须多源交叉。** 单一源（尤其教育网源）测出的是路由质量，
不是带宽上限。

### 2.1 远端到不同源（单线程，每档 8–10s）

| 源 | 单线程 | 4 线程 |
|---|---|---|
| **华为云** `mirrors.huaweicloud.com` | **89–92 MB/s** | 74.93 MB/s |
| 中科大 USTC | 0.02 MB/s（403） | — |
| 清华 CERNET `mirrors.tuna.tsinghua.edu.cn` | 1.12 MB/s | 1.05 MB/s |
| 阿里云 | 302 | — |
| 腾讯云 | 404 | — |
| 网易 163 | 连接失败 | — |

**华为云 vs 清华差 80 倍**，同一台机器同一时刻。

### 2.2 网卡实时采样（华为云下载中）

```
第1秒 85.33 → 第2秒 88.88 → 第3秒 91.47 → 第4秒 92.73 → 第5秒 93.99 MB/s
```

稳定 90+ MB/s ≈ **720 Mbps**，千兆网卡跑到约 72%。**物理带宽充足。**

### 2.3 经渡口 vs 直连（同一华为云源）

| 通道 | 吞吐 |
|---|---|
| 渡口 HTTP 代理（10809） | **36.47 MB/s** |
| 渡口 SOCKS5（10808） | 20.37 MB/s |
| 本机直连 | 7.80 MB/s |

**渡口比本机直连快 4.7 倍** —— 因为远端办公网出口比学校 WLAN 出口好。

### 2.4 结论

- 瓶颈**不在**网卡（千兆，实跑 720Mbps）、**不在** SSH 隧道（零损耗）
- 吞吐由**下载源的路由质量**决定，同一台机器不同源差 80 倍
- 大文件优先选华为云 / 阿里云，避免教育网源

## 三、DNS（2026-10-23）

### 3.1 响应速度（5 个域名 × 3 次）

| DNS 服务器 | 成功 | p50 | avg |
|---|---|---|---|
| `10.10.1.10`（内网） | 15/15 | **1ms** | **1ms** |
| `10.10.1.9`（内网） | 15/15 | 1ms | 12ms |
| `192.168.100.1` | 15/15 | 7ms | 6ms |
| `223.5.5.5` | 15/15 | 7ms | 7ms |
| `119.29.29.29` | 15/15 | 7ms | 7ms |

### 3.2 github.com 解析结果（决定性）

5 个 DNS 服务器 + 2 个 DoH 渠道（阿里 / doh.pub）**全部返回同一 IP**。
说明这是 GitHub 权威 DNS 的真实记录，**不是污染**。

→ **换 DNS 无法改善 github 可达性。** 这一点直接否掉了「换 DNS 能解决卡顿」的方向。

### 3.3 渡口时的 DNS 路径

`ssh -D` 用 SOCKS5 的 `ATYP=0x03`（域名）转发，**由远端解析**。
本机 `lookup` 耗时 0.00003s（不解析），远端承担真实解析。

## 四、github 可达性根因

### 4.1 DNS 给的 IP 恰好是坏的

远端办公网把 `github.com` 解析到 `20.205.243.166`，该 IP 在远端多次采样
只有 2/5 ~ 0/3 可达；而其他候选 IP 多为 5/5。

### 4.2 修复：候选 IP 池 + 并行竞速

`tools/smart-resolve.mjs` 维护候选池，按健康分排序，Happy Eyeballs 式
并发发射（4 路，间隔 400ms），任一成功即返回，总预算 8s。

**健康分只统计最近 60 秒**的事件。早期版本用累加计数，常驻进程跑几百次后
所有 IP 分数全负、排序失效，表现为「前 9 次全失败、后 6 次全成功」。

### 4.3 部分域名必须交给远端解析

`raw.githubusercontent.com` / `gist.*` / `objects.*` **刻意不进候选池**。

取证（同时刻双路径对比，各 6 次）：

```
远端直连（不经隧道）：000 301 000 000 000 000
经本工具隧道        ：000 000 200 000 000 000
```

两者成功率一致（约 1/6）→ 是办公网到 GitHub Fastly 边缘（`185.199.x` /
`151.101.x`）的链路问题，与本工具无关。放进池里反而会让「TCP 通但 TLS 被 RST」
的 IP 被当成好 IP，白耗一次超时预算。

## 六、断网可用性（2026-10-23，在 xt 上实测）

### 6.1 为什么要用另一台机器做

模拟断网会切断本机所有公网出站（含远程会话本身）。在 `xt`（10.113.66.6）上做，
本机与它的 SSH 走局域网，不受影响，实验可完整跑完并自动还原。

### 6.2 断网怎么模拟

**不能用防火墙**。两个原因：

1. `xt` 的防火墙三个 profile 全是 `Disabled`，加规则无效（实测直连仍通）
2. 即使启用，**Windows 出站规则里 `Allow` 优先于 `Block`** —— 系统自带
   60~80 条 Allow 会把新增的 Block 全部盖掉

**改用路由表**，这也更贴近学校「禁用上网但局域网通」的真实状态：

```powershell
# 断网 = 删默认路由（去公网没出口）
Remove-NetRoute -DestinationPrefix '0.0.0.0/0' -ifIndex 15 -NextHop 10.113.64.1
# 保局域网（含本机网段与远端网段）
New-NetRoute -DestinationPrefix '10.0.0.0/8' -ifIndex 15 -NextHop 10.113.64.1
```

### 6.3 实测结果

```
[4] 确认公网确实断了：
      直连 myip   : FAIL(000)
      直连 baidu  : FAIL(000)
      直连 github : FAIL(000)
      公网已断    : True          ← 前提成立

[5] 断网状态下经渡口：
      github.com       : OK
      api.github.com   : OK
      baidu.com        : OK
      bilibili.com     : OK
      渡口出口         : 218.107.0.47（联通，远端出口）
      （xt 自己的出口是 116.23.159.136 电信，两者不同即证明走的是另一条路）

[6] 20 秒持续采样：4/4

RESULT: PASS — 断网后渡口可用
```

### 6.4 结论的适用边界

| 断网类型 | 渡口是否有效 |
|---|---|
| **禁用上网权限、局域网仍通**（本校情况） | ✅ **有效**（已验证） |
| WLAN 接入层断开（拿不到 IP / 没有网关） | ❌ 无效 —— SSH 也起不来 |

第二种情况需要另一条物理通路（手机热点 / 随身 WiFi），这是方案的最大单点。

## 七、WireGuard 未投入使用

远端 `WireGuardTunnel$wg0` 服务是 `Running/Automatic`，但：

- 本机从未安装 WireGuard 客户端，无 `wg0` 适配器
- 远端 `wg show dump` 显示 peer 的 `latest handshake` 从未发生
- 实际承载流量的是 `ssh -D` 动态转发

结论：**这套配置不参与数据流**，保留仅为将来可能的多出口分流。
不要误以为流量经过它。
