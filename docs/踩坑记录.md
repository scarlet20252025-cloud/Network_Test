每条都是实测撞出来的。写新脚本前先扫一遍，能省几小时。

## 一、PowerShell 5.1 相关（最坑的一类）

### 1. `.ps1` 必须 UTF-8 **with BOM**

`write` 工具写出的 `.ps1` 没有 BOM，PS 5.1 会把无 BOM 的 UTF-8 当 ANSI 读，
中文注释直接破坏语法，**报错位置还会指向无关的行**。

```powershell
# 每次写完/改完都要补 BOM，且 edit 之后 BOM 可能再次丢失
$f = 'xxx.ps1'
[IO.File]::WriteAllText($f,
  [IO.File]::ReadAllText($f, [Text.Encoding]::UTF8),
  (New-Object Text.UTF8Encoding($true)))
# 验证前 3 字节 = 239,187,191
[IO.File]::ReadAllBytes($f)[0..2] -join ','
```

### 2. `if` 不能当表达式用

```powershell
# pwsh 7 可以，PS 5.1 报 Missing statement block after if
$shown = if ($x) { 'a' } else { 'b' }

# 正确
$shown = 'b'
if ($x) { $shown = 'a' }
```

同样禁止出现在哈希表字面量里：
`@{ Total = if($st){$st.P50}else{$null} }` → 先算到变量再赋值。

### 3. 枚举必须写完整类型

```powershell
# 报「无法将标识符名称 FormWindowState.Normal 与有效的枚举器名称相匹配」
$form.WindowState = 'FormWindowState.Normal'

# 正确
$form.WindowState = [System.Windows.Forms.FormWindowState]::Normal
```

`CloseReason` 同理：`[System.Windows.Forms.CloseReason]::UserClosing`。

### 4. `Invoke-WebRequest -Proxy socks5://` 不支持

```
The ServicePointManager does not support proxies with the socks5 scheme.
```

同一个函数在 pwsh 7.6.6 下全过，在 PS 5.1 下全 FAIL。
**改用 `curl.exe`**：`--socks5-hostname 127.0.0.1:10808`（渡口）/ `--noproxy '*'`（直连）。

### 5. `Test-NetConnection` 对关闭端口要等满 14.3 秒

实测 14295ms 才返回 False（Win10 SYN 无响应等满超时）。
每次界面刷新都调它 → GUI 启动卡 14 秒、每 10 秒自动刷新又卡 14 秒。

```powershell
# 正确：TcpClient 异步 + 300ms 超时，实测 525ms 返回
$c = New-Object Net.Sockets.TcpClient
$iar = $c.BeginConnect('127.0.0.1', $port, $null, $null)
$ok = $iar.AsyncWaitHandle.WaitOne(300, $false)
$c.Close()
```

### 6. `Start-Process -Command <长脚本>` 传参会坏

要跑临时脚本必须先写文件再 `-File`，且同样要补 BOM。

## 二、网络/代理相关

### 7. 系统代理会污染出口 IP 探测

本机系统代理是 Clash Verge `127.0.0.1:7897`，`Invoke-WebRequest` **默认读系统代理**，
直连探测拿到的其实是 Clash 出口。

三源对照暴露真相：
- `myip.ipip.net` → 198.51.100.10（走 Clash）
- `members.3322.org/dyndns/getip` → 141.11.146.75（绕过 Clash，**真实**）
- `ip.3322.net` → 198.51.100.10（走 Clash）

**修法**：直连探测必须 `--noproxy '*'` / `-Proxy $null`。

### 8. 出口 IP 必须双通道对照

只看「渡口出口」不看「直连出口」会误判。
`On` 之后**直连查询反而不通、渡口通**，才是系统级真的在走远端。
两个不同 IP（直连 198.51.100.10 电信 / 渡口 203.0.113.47 联通）才是铁证。

### 9. curl 测 HTTPS 大文件会被证书吊销检查挡住

```
curl: (35) schannel: next InitializeSecurityContext failed:
CRYPT_E_REVOCATION_OFFLINE (0x80092013)
```

**修法**：加 `--ssl-no-revoke`。
注意这跟网络无关 —— 直连和渡口会同时失败，容易被误判成「渡口不通」。

### 10. `--proxy socks5h://` 的 h 很关键

`socks5://` 本地解析 DNS，`socks5h://` 交给代理解析。
实测渡口 lookup 时间从 0.0136s 降到 0.000036s —— 本地完全不做 DNS。
副作用：本机 hosts 文件对渡口流量不生效。

## 三、远端操作相关

### 11. `$priv | wg pubkey` 在 SSH 下会挂

```
Cannot process the XML from the 'Error' stream of ssh.exe:
Data at the root level is invalid. Line 1, position 1.
```

**修法**：`& cmd /c "echo <priv> | wg.exe pubkey"`

### 12. 远端 Windows PowerShell 5.1，没有 pwsh 7

所有远程命令必须 `powershell -NoProfile -EncodedCommand <base64>`，
不要用 `pwsh`，也不要在命令行里嵌引号（会被 bash/ssh 二次解释吃掉）。

```powershell
function RemotePS([string]$script){
  $enc = [Convert]::ToBase64String([Text.Encoding]::Unicode.GetBytes($script))
  ssh -o ConnectTimeout=8 pcs "powershell -NoProfile -EncodedCommand $enc"
}
```

### 13. WireGuard 官方下载地址已变

**正确**：`https://download.wireguard.com/windows-client/wireguard-amd64-1.1.1.msi`
旧的 `windows-x86_64/wireguard-installer.exe` 全部 404。
本机直连该域名不通，**必须走代理 127.0.0.1:7897**。

### 14. 远端 WinNAT 组件未安装（放弃 NAT 的根据）

`New-NetNat` 报「无效类」，取证：
- `System32\wbem\netnatcim.dll` = False
- `WinSxS` 中无 `netnatcim.dll` → 组件确实未安装
- `root/StandardCimV2` 只有 `MSFT_NetNatTransition*` 三类，**无 `MSFT_NetNat`**
- `Get-WindowsOptionalFeature` 无 NAT/Routing 可选功能
- `netsh routing ip nat` 命令不存在

**结论：放弃远端 NAT，改走 SSH SOCKS。**

## 四、WinForms / GUI 相关

### 15. `ShowDialog()` 是模态循环，最小化就退出

日志证据：`最小化 → FormClosing reason=None → FormClosed → 消息循环结束`，进程直接没了。
**修法**：`[System.Windows.Forms.Application]::Run($form)`。

### 16. 改 `ShowInTaskbar` 会 `RecreateHandle()` → 黑块

句柄重建瞬间子控件来不及重绘，露出窗体底色（整片黑块）。
**修法**：全程不碰 `ShowInTaskbar`，用 `Hide()`/`Show()` 做托盘化。
另加 `DoubleBuffered=true`（反射取非公开属性）。

### 17. `NotifyIcon` 图标在 Win11 会被折叠进溢出区

`NotifyIcon.Visible = true` **是生效的**，图标确实注册成功了，
但 Win11 默认把它放进「^ 显示隐藏的图标」溢出区，主托盘区看不到。

**验证方法**（别只看截图）：
```powershell
# 点开溢出区后枚举
$root = [System.Windows.Automation.AutomationElement]::RootElement
# 溢出窗口类名是 TopLevelWindowForOverflowXamlIsland（不是 NotifyIconOverflowWindow）
```

**固定到主托盘区**：只能由用户手动在
`设置 → 个性化 → 任务栏 → 其他系统托盘图标` 里打开开关。
程序侧**做不到**（注册表 `HKCU:\Control Panel\NotifyIconSettings` 的 key
是自定义 hash，不是 FNV 系列，已实测 48 种组合全部不命中；
`SendInput` 拖拽对 XAML 溢出岛也无效，已试 `mouse_event` 与 `SendInput` 相对位移两版）。

**另一个坑**：`NotifyIconSettings` 按 **exe 身份**记录。
所有寄生在 `powershell.exe` 上的托盘图标**共享同一条记录**，
所以多个 PS 脚本的托盘图标会互相覆盖（本机实测：`powershell.exe` 只有一条，
tooltip 是 `Codex Dream Skin`，我们的图标根本没独立条目）。

## 20. git 走隧道时 schannel 后端会失败，必须换 openssl

**现象**：

```
git -c http.proxy=socks5h://127.0.0.1:10808 push
→ fatal: unable to access '...': schannel: failed to receive handshake, SSL/TLS connection failed

git -c http.proxy=http://127.0.0.1:10809 push
→ fatal: unable to access '...': schannel: server closed abruptly (missing close_notify)
```

但同一个代理端口用 `curl` 和 `Invoke-WebRequest` 访问 github 都是 200。

**根因**：Windows git 默认 `http.sslBackend=schannel`（走 Windows SChannel API）。
SChannel 在「经代理 CONNECT 隧道」的场景下对 `close_notify` 和重协商处理更严格，
隧道对端关闭方式稍有不同就报 `server closed abruptly`。

**修法**：加 `-c http.sslBackend=openssl`

```bash
git -c http.version=HTTP/1.1 -c http.proxy=http://127.0.0.1:10809 -c http.sslBackend=openssl push origin main
```

实测立即成功：`3c953e6..7a046ab  main -> main`。

**注意**：本机 git 走 HTTP/2 会卡 TLS renegotiate，所以 `http.version=HTTP/1.1`
是必需参数（这条早就记录过）。现在**两个参数都必需**：
`http.version=HTTP/1.1` + `http.sslBackend=openssl`。

**另外**：优先用 `http.proxy=http://127.0.0.1:10809`（dual-proxy）而不是
`socks5h://127.0.0.1:10808`（裸 ssh -D）—— 前者带 IP 择优，成功率明显更高。

## 21. PowerShell 里 `cd` 不影响 .NET 的当前目录

**现象**：`cd 'E:\肥鱼不乐园\ferry'` 之后，
`[IO.File]::ReadAllText('docs\踩坑记录.md', ...)` 报
`Could not find a part of the path 'E:\肥鱼不乐园\docs\踩坑记录.md'`。

**根因**：PowerShell 的 `Set-Location` 只改 PowerShell 自己的 `$PWD`，
不改进程级的 .NET 当前工作目录。`[IO.File]` 这类 .NET 静态方法用进程 CWD，
所以相对路径解析到了父目录。

**修法**：给 .NET 方法**一律用绝对路径**；只有 PowerShell 原生命令
（`Get-Content`、`git`、`curl.exe`）才认 `cd`。

## 23. 备份文件把「渡口地址」存成了「原始值」，导致切回直连后全网不通

**现象**：用户点「切回直连」后所有网站打不开，而点「开启渡口」正常。

**根因**：`proxy-backup.txt` 内容是 `True|http://127.0.0.1:10809` ——
**备份里存的就是渡口地址本身**。

于是「切回直连」= 把系统代理还原成 `http://127.0.0.1:10809`，
但那时隧道已经被停掉了 → 所有流量指向一个没人监听的端口 → 全部打不开。

**怎么被污染的**：我调试时手动把系统代理设成 `http://127.0.0.1:10809` 验证连通性，
紧接着 GUI 又跑了一次「开启渡口」，它把「当前值」当成「原始值」备份了下来。

**用户的真实原始代理是 Clash Verge 的 `127.0.0.1:7897`**
（`verge.yaml` 里 `enable_system_proxy: true`，`mixed-port: 7897`）。

**修复**（`ferry.ps1` 与 `渡口助手.ps1` 各一份，逻辑完全一致）：

```powershell
function Test-BorrowProxyValue {
  param([string]$Server)
  $s = $Server.Trim()
  return ($s -eq "127.0.0.1:$SocksPort") -or ($s -eq "http://127.0.0.1:$HttpPort") -or
         ($s -eq "127.0.0.1:$HttpPort") -or ($s -eq "http://127.0.0.1:$SocksPort")
}

function Save-ProxyBackup {
  $cur = Get-ProxyState
  # 规则1：当前值就是渡口地址 → 绝不备份它
  if (Test-BorrowProxyValue $cur.Server) { return }
  # 规则2：已有有效备份就不覆盖（保留最原始的 Clash/直连设置）
  ...
}

function Restore-ProxyBackup {
  # 规则3：备份内容本身是渡口地址 → 判定无效
  # 规则4：无效备份时优先回落 Clash(7897)，其次关闭系统代理
  # 规则5：备份指向的端口没监听 → 不指过去，直接关代理
}
```

**三条硬规则**：

1. **绝不把渡口地址存进备份** —— 备份的意义是「渡口之前的样子」
2. **还原前检查目标端口是否监听** —— 指向死端口的代理比没有代理更糟
3. **无效备份要有兜底** —— 回落 Clash（用户原本的代理），再不行就关代理

**另一个顺序坑**：必须先还原代理、再停隧道。
反过来会让「端口是否监听」的检查失去意义（此时渡口端口已经关了）。

**验证**（`On` → `Off` 完整跑一遍）：

```
On  : 跳过备份：当前代理是渡口地址  →  代理=http://127.0.0.1:10809
Off : 已还原为 ProxyEnable=1 ProxyServer=127.0.0.1:7897
      → baidu 200 / bilibili 200 / github 200
```

## 24. 给流加 `'data'` 监听后再 `pipe()`，数据会被两方争抢导致丢字节

**现象**：给 dual-proxy 加上「确认上游是否真能回数据」的逻辑后，
`github.com` 从修好前 10/10 掉到 4/10，且失败是 20s 超时而不是秒失败。

**错误做法**（第一版）：

```javascript
sock.on('data', onData);   // 为了数上游回了多少字节
sock.pipe(clientSocket);   // 又交给 pipe 转发
```

**根因**：给 Socket 加 `'data'` 监听会让流切换到 **flowing 模式**，
触发 pipe 的自动转发会被这个监听器抢先消费掉一部分字节。
TLS ClientHello 的响应首字节丢了，握手就永远完成不了 —— 表现为「卡到超时」。

**正解**：自己转发，一个字节都不丢。

```javascript
function pipeWithConfirm(src, dst, confirm, label) {
  let bytes = 0;
  src.on('data', (chunk) => {
    if (bytes === 0) settle(true);   // 首个字节即证明链路通
    bytes += chunk.length;
    if (!dst.write(chunk)) src.pause();   // 背压
  });
  dst.on('drain', () => src.resume());
  src.on('end', () => { if (dst.writable) dst.end(); });
  src.on('error', () => dst.destroy());
}
```

修好后 `github.com` 恢复 **15/15，p50 2.2s**。

**教训**：Node 流里「观察」和「消费」是同一件事。要观测字节数就必须自己写转发，
不能既挂 `'data'` 又 `pipe()`。

## 25. 只验证 TCP 建连的「择优」，对 TLS 被 RST 的目标等于没做

**背景**：`smart-resolve.mjs` 的 `connectBest()` 只做到 SOCKS5 建连成功（TCP 三次握手），
就 `markOk(ip)`。

**问题**：`raw.githubusercontent.com` / `github.com` 都有
「**TCP 通、TLS 握手被中间设备 RST**」的 IP。这些 IP 会被永久当成好 IP，
排序永远排在前面，用户看到的却是「择优成功但浏览器连接被重置」。

**修法**：`connectBest` 加 `deferConfirm` 选项，返回 `confirm(ok, detail)` 回调，
由调用方在**应用层**跑通后再标记健康：

```javascript
const r = await connectBest(host, port, { deferConfirm: true });
// ...建立隧道后
pipeWithConfirm(r.sock, client, r.confirm, `${host}@${r.ip}`);
```

**验证脚本**（`.ferry/probe-raw2.mjs` 的思路）：完整跑
SOCKS5 → TLS(SNI=域名) → HTTP GET，只有拿到 200/301 才算通。
实测 12 个候选 IP 里通常只有 1–2 个能达到这一步。

## 26. 有些目标修不了就别硬修：识别「不是本工具的锅」

**发现**：`raw.githubusercontent.com` 无论怎么试都约 1/6 成功率。
取证方法 —— **同时刻对比远端直连与经隧道**：

| 方式 | 6 次结果 |
|---|---|
| 远端直连（不经隧道） | 000 301 000 000 000 000 |
| 经本工具隧道 | 000 000 200 000 000 000 |

两者成功率一致 → 是办公网到 GitHub Fastly 边缘（`185.199.x` / `151.101.x`）的链路问题。

**处置**：把 `githubusercontent.com` 整族从候选池里**移除**（映射到 `null`，
交给远端 DNS 正常解析），而不是继续往里堆固定 IP。

**为什么移除比保留好**：留在池里会让 `connectBest` 把「TCP 通但 TLS 被掐」的 IP
当成功，白白多等一个超时才回落，反而更慢。

**教训**：排查到「本工具的路径与直连路径表现一致」时，就该停手并记录证据，
不要靠堆更多重试/固定 IP 去掩盖上游问题。

## 27. `curl --noproxy '*'` 会**覆盖** `-x`，让「走代理」的测量全变假象

**现象**：测 mihomo 三态出口时，切到 `ferry-ssh` 后仍然返回 DIRECT 的出口 IP，
三条线全是电信，看起来像分流规则没生效。

**真相**：命令里写了 `curl --noproxy '*' -x http://127.0.0.1:10810 ...`。
`--noproxy '*'` 的意思是「对所有主机禁用代理」，**优先级高于 `-x`** ——
请求根本没走代理，测到的一直是本机直连出口。

**正确写法**：只写 `-x`，不要加 `--noproxy`。

```powershell
# 错
curl.exe --noproxy '*' -x http://127.0.0.1:10810 https://myip.ipip.net
# 对
curl.exe -x http://127.0.0.1:10810 https://myip.ipip.net
```

**教训**：测代理是否生效，先确认「代理真的被用了」。一个禁代理由的参数
能让整轮实验的结论全部作废，而且看起来非常像被测对象有 bug。

## 28. PS 5.1 `Invoke-WebRequest -Proxy` 会复用连接池，测出上一态的结果

**现象**：脚本里用 `Invoke-WebRequest -Proxy http://127.0.0.1:10810` 依次测
DIRECT / ferry-ssh / ferry-wg 三态，三个都返回同一个 IP。

**原因**：`Invoke-WebRequest` 走 `ServicePoint` 连接池，对**同一主机**
（`myip.ipip.net`）的连接被上一次请求的上游缓存下来，切线路后仍然复用旧连接。

**修法**（两条一起用）：

1. 换 `curl.exe` —— 每次新连接，没有连接池；
2. 切换后 `Start-Sleep -Milliseconds 1000`，等 mihomo 把新选择应用到新建连接
   （300ms 时偶发读到上一态）。

另外 PS 5.1 捕获外部程序 stdout 时按控制台 OEM 代码页（936）解码，而 curl
输出是 UTF-8，直接 `$r = & curl.exe ...` 会得到 `褰撳墠 IP锛?16...` 这种
二次编码乱码。**落盘后按 UTF-8 读**：

```powershell
$null = & curl.exe -s --max-time 15 -x "http://127.0.0.1:$MixedPort" -o $tmp 'https://myip.ipip.net'
$r = [Text.Encoding]::UTF8.GetString([IO.File]::ReadAllBytes($tmp))
```

## 29. `[Diagnostics.Process]::Start` 起的后台进程会被 Job 对象回收

**现象**：mihomo 拉起后日志显示「已就绪」，端口也在听，但两分钟后端口消失。

**原因**：`Process::Start` 创建的子进程落在父进程的 Job 对象里。当父进程是被
DSH 的 `ops_bash` / `pwsh` 后台任务拉起时，任务一结束（或被 cancel），
整棵进程树被回收。

**修法**：用 WMI 创建，父进程是 `WmiPrvSE`，不属于调用方的 Job：

```powershell
$res = Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{
  CommandLine      = $cmd
  CurrentDirectory = $Here
}
$newPid = [int]$res.ProcessId
```

**顺带的好处**：`Process::Start` 在 `UseShellExecute=false` + `Redirect=false`
时子进程会继承 stdout 句柄，导致调用方的管道**永不 EOF**，前台调用直接卡到
超时（实测 60s）。WMI Create 无句柄继承，一并解决。

## 30. `.cmd` 必须 **GBK + 无 BOM + CRLF**，三条缺一条就炸

这是本项目第二次栽在批处理编码上（`b2e0df1` 那次是 UTF-8 乱码）。

| 缺失项 | 实测报错 |
|---|---|
| 带 BOM | `'∩╗┐@echo' 不是内部或外部命令` —— cmd.exe 把 BOM 三个字节当命令的一部分，首行 `@echo off` 失效 |
| 纯 LF 换行 | `'em' 不是内部或外部命令` —— 解析器把行尾 CR 当命令终止符，纯 LF 会**吃掉每行第一个字符**，`rem ...` 变成 `em ...` |
| UTF-8 编码 | `chcp 936` 下中文注释变乱码 |

正确写法（PS 5.1）：

```powershell
$content = ($content -replace "`r`n", "`n") -replace "`n", "`r`n"   # 强制 CRLF
$gbk = [Text.Encoding]::GetEncoding(936)
[IO.File]::WriteAllText($CmdPath, $content, $gbk)
```

**注意**：PowerShell 的 here-string 用的是宿主文件的换行符。如果 `.ps1`
本身是 LF（`write` 工具写出来的就是 LF），here-string 里也是 LF —— 所以
必须显式 `-replace` 转换，不能指望它自带 CRLF。

## 31. 按进程名杀进程会杀掉 Clash Verge 的 `verge-mihomo`

**现象**：想重启渡口的 mihomo，用 `Get-Process verge-mihomo | Stop-Process`，
结果用户的 Clash Verge 也断了。

**原因**：本机同时常驻两个同名进程 —— Clash Verge 自己的
`D:\Clash Verge\verge-mihomo.exe`，和渡口复制出来的同一个二进制。
进程名完全一样。

**也不能靠命令行匹配**：跨会话读 `Win32_Process.CommandLine` 常常是空的
（权限），匹配会漏，漏了就杀错。

**修法**：用 **PID 文件**做唯一凭据，并校验那个 PID 确实还是 `verge-mihomo`：

```powershell
function Get-MiProc {
  if (-not (Test-Path $PidPath)) { return $null }
  $procId = 0
  if (-not [int]::TryParse((Get-Content $PidPath -Raw).Trim(), [ref]$procId)) { return $null }
  $p = Get-Process -Id $procId -ErrorAction SilentlyContinue
  if (-not $p) { return $null }
  if ($p.ProcessName -ne 'verge-mihomo') { return $null }
  return $p
}
```

**同类坑**（`tools/ssh-tunnel-keeper.ps1` 已踩过）：单例锁只比 PID 不够 ——
强杀会留下 lock 文件，Windows 会把那个 PID 复用给任意新进程，新进程看到
「PID 存在」就自杀。必须同时校验该 PID 的命令行里真的有本脚本名。

## 32. `store-selected: false` + 看护重启 = 借网状态被静默清掉

**背景**：`config.template.yaml` 里设了 `profile.store-selected: false`，
目的是「开机默认永远是 DIRECT，不自动借网」。这是对的。

**副作用**：看护循环（Watch）在上游端口顺延时会重启 mihomo，而 mihomo

## 34. 提权进程的 `CommandLine` 读不到 —— `-like` 对 null 返回 false

**现象**：`mihomo-keeper.ps1 -Action Watch` 本该单例运行，实测堆出了 **5 个**同时跑，
每个都在无效重启 mihomo，任务管理器里十几条进程。

**根因**：

```powershell
return ($proc.CommandLine -like '*mihomo-keeper.ps1*' -and $proc.CommandLine -like '*Watch*')
```

管理员权限启动的进程，普通权限查它的 `CommandLine` 拿到的是 **null**（跨完整性级别的限制）。
而 `$null -like '*x*'` 返回 **false** —— 于是判定「旧的那个已经死了」，
接管锁，又起一个。

**修法**：命令行读不到时**保守认为它还活着**。

```powershell
if (-not $proc.CommandLine) { return $true }   # 读不到 = 不确定 = 当活着
return ($proc.CommandLine -like '*mihomo-keeper.ps1*' -and $proc.CommandLine -like '*Watch*')
```

**更好的修法**：单例别用 PID 文件，用**命名 Mutex**。

```powershell
$mutex = New-Object System.Threading.Mutex($false, 'Local\FerryMihomoWatch')
$got = $false
try { $got = $mutex.WaitOne(0) }
catch [System.Threading.AbandonedMutexException] { $got = $true }   # 上个持锁进程被强杀
if (-not $got) { exit 0 }
```

Mutex 是内核对象：进程退出自动释放，没有「残留文件」和「PID 复用」问题。
实测 3 个并发只有 1 个拿到锁。

**教训**：任何「靠读别的进程信息判断它是否活着」的逻辑，都要考虑**读不到**这种情况。
读不到 ≠ 已经死了。

## 35. 已提权的安装器用 CreateProcess 启动 requireAdministrator 的 exe → 错误 740

**现象**：安装过程中弹框：

```
无法执行文件: ...\渡口助手.exe
CreateProcess 失败；错误代码 740。请求的操作需要提升。
```

但程序本身还能正常启动 —— 所以很容易当成小毛病忽略。

**根因**：
- 安装器 `PrivilegesRequired=admin`，**已经提权**
- 客户端 exe 的 manifest 是 `requireAdministrator`
- Inno Setup 的 `[Run]` 用 `Flags: runhidden waituntilterminated` 时走 **CreateProcess**

从高完整性进程用 CreateProcess 启动一个同样要求提权的 exe 会直接失败
（`ERROR_ELEVATION_REQUIRED` = 740）—— **CreateProcess 不会触发 UAC**。

另一条 `[Run]` 带 `postinstall nowait`，Inno 对它用 ShellExecute，能正常提权，
所以「程序能启动」和「自启那步报错」同时存在。

**修法**：不要在 [Run] 里传参调用它。改成**标记文件**：

```pascal
{ Inno 的 [Code] 段 }
if WizardIsTaskSelected('autostart') then
  SaveStringToFile(ExpandConstant('{app}\.want-autostart'), '1', False);
```

客户端启动时（本来就是管理员）读到标记 → 建计划任务 → 删标记。
它调 schtasks 毫无问题。

**为什么不在安装器里直接调 schtasks**：`/TR` 要传带引号的完整路径，
Inno 的 Pascal 里得写 `""""path""""` 四层引号，路径含空格时行为还不确定。
让客户端自己调最稳 —— 它知道自己叫什么、装在哪。

**标记的落点要注意**：放在「写 config.json」那段**之前**。
那段在「保留已有激活」时会 `exit`，放后面的话重装场景永远不会装自启。

## 36. 系统代理「只关开关、不更新地址」会留下脏值

## 37. 计划任务以 SYSTEM 跑时，`%LOCALAPPDATA%` 指向 systemprofile

**现象**：管理面板上改限速，界面显示「已生效 每 IP 10 MB/s」，实际测速还是老值。

**根因**：门户是计划任务起的，owner 是 `NT AUTHORITY\SYSTEM`。那时

    %LOCALAPPDATA% = C:\Windows\System32\config\systemprofile\AppData\Local

而不是 `C:\Users\PCserver\AppData\Local`。于是门户找不到中继脚本目录，
回落到 systemprofile 路径 —— 读不到 `rate-mb.txt` 就返回默认值，
写配置也写到了 SYSTEM 的目录，中继完全不知道。

2. 候选目录**打分**：有 `rate-mb.txt` 的 +100（说明是真在用的），有中继脚本的 +10
3. 把 `relayDir` / `rateFile` / `rateFileExists` / `isSystem` 暴露到 API 上，

**教训**：用 `%LOCALAPPDATA%`、`~`、相对路径去定位「另一个程序的文件」时，

## 38. `Task.Factory.StartNew` 包同步阻塞 IO = 线程池反模式

**现象**：客户端 40 个连接时 **61 个线程、64 MB 内存**。

**根因**：

```csharp
var t1 = Task.Factory.StartNew(delegate () { copy(a, b, true); });   // copy 里是同步 src.Read
var t2 = Task.Factory.StartNew(delegate () { copy(b, a, false); });
```

线程池遇到「一堆长时间阻塞的任务」只肯**每秒注入 1~2 个新线程**，
连接一多就严重积压。更糟的是同一个线程池上还跑着心跳上报、
授权检查、UI 回调 —— 它们会被一起饿死，整机跟着卡。

**修法**：明确知道是阻塞的活，就用**专用线程**，别占线程池配额。

```csharp
Thread th1 = new Thread(delegate () { try { copy(a, b, true); } finally { anyDone.Set(); } });
th1.IsBackground = true;
th1.Start();
```

改完：**内存 64 MB → 24 MB**，线程 61 → 48。

**顺带加了并发上限**（400 连接）：TUN 全局接管时本机所有连接都进这里，
浏览器多开就是几百连接。无上限会顶到上千线程 + 句柄上限
（实测 40 连接已经 984 句柄）。超限直接关连接 —— HTTP 客户端会重试，
比让整机卡死好。

**教训**：`Task.Run` / `StartNew` 只适合**真异步**或**短任务**。
包一个阻塞的 `Stream.Read` 进去，等于给线程池埋雷。

## 39. CSRF token 每次渲染都换 → 任何局部更新都会 403

**现象**：改完第一条备注，改第二条或点「停用」就 403。
控制台不报错，界面上就是「保存失败」。

**根因**：`csrf_set()` 的实现是「每次调用都生成新 token 并覆盖」：

```python
def csrf_set(key):
    tok = new_csrf()
    _csrf[key] = tok      # ← 覆盖旧的
    return tok
```

整页刷新的老流程看不出问题（每次提交都重新渲染并带回新 token）。
但一旦有 fetch / 局部更新就炸：服务端悄悄轮换了 token，
页面上其他表单还拿着旧的。

**修法**：会话内稳定，只在登录成功时主动轮换一次（防会话固定）。

```python
def csrf_set(key):
    if key not in _csrf:
        _csrf[key] = new_csrf()
    return _csrf[key]

def csrf_rotate(key):        # 登录时调
    _csrf[key] = new_csrf()
    return _csrf[key]
```

token 仍然随机不可猜、绑定客户端 IP、只活在本进程内。
失去的只是「每次请求换一次」这个额外保护，而代价是随时可能 403。

**教训**：设计 CSRF token 生命周期时要先想清楚**页面会不会局部更新**。
如果会，token 必须比「一次渲染」活得更久。

## 40. UDP 关联「定义了超时常量却从没用过」

**现象**：日志里几秒一个 `UDP ASSOCIATE`，正常用一整天能堆几千个。

**根因**：`UDP_IDLE_TIMEOUT = 60` 这个常量定义了，
`last_active` 每次都更新 —— **但没有任何代码读它**。等于没有回收。

每个 UDP 关联占 **2 个 UDP 端口**（`client_sock` + `target_sock`）。
关联的生命周期绑定 TCP 控制连接：客户端正常断开时 EOF 立刻回收，
但客户端**异常**断开（进程被杀、休眠、拔网线）时没有 FIN，
要挂到 TCP 超时（几分钟）。Windows 动态端口默认 16384 个 → 约 8000 个关联就耗尽。

**修法**：
- 全局 `_relays` 登记表 + 硬上限 3000
- 每 30 秒回收 `now - last_active > UDP_IDLE_TIMEOUT` 的
- 日志带上「当前关联 N 个」，不看面板也能判断水位

**教训**：定义了常量 ≠ 实现了功能。写完之后 grep 一下这个常量有没有被**读**过。

## 44. Job Object 会把「要交接给外部的进程」一起杀掉

**现象**：点「开启全局模式」→ 程序退出 → 约 1 秒后又起来 → 但状态仍显示
「TUN 需要管理员权限」。日志里能看到新实例确实启动了，只是没有管理员权限。

**原因**：客户端启动时建了一个 Job Object（`JobKeeper`），带
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`、没有 `BREAKAWAY_OK`。之后所有子进程
（包括 `UseShellExecute = true` 起的）都落在这个 Job 里。父进程退出 → Windows
回收整个 Job。更隐蔽的是：**在 Job 上下文里，ShellExecute 的 `runas` 会静默失败
并回退成普通权限启动** —— 不报错、不弹 UAC，新进程照起，只是没有令牌。

**处理**：用 WMI 起中转进程，它的父是 `WmiPrvSE.exe`，不在我们的 Job 里：

```csharp
using (var mc = new ManagementClass("Win32_Process")) {
    var p = mc.GetMethodParameters("Create");
    p["CommandLine"] = "powershell.exe -NoProfile -WindowStyle Hidden -Command \"...Start-Process -Verb RunAs\"";
    mc.InvokeMethod("Create", p, null);
}
```

**验证方法**：让提权进程跑 `whoami /groups`，输出里要有
`Mandatory Label\High Mandatory Level S-1-16-12288`。光看「进程起来了」不够。

**教训**：这个坑一天内踩了两次 —— 第一次以为改 `UseShellExecute=true` 就脱离了
Job（并没有），第二次才发现必须换启动方式。**「进程起来了」不等于「权限对了」**。

## 45. Inno 的 `/CLOSEAPPLICATIONS` + 托盘程序 = 静默失败

**现象**：点「更新」→ 提示有新版本 → 点「是」→ 下载完成（`%TEMP%` 里能看到
17 MB 的安装包）→ 然后什么都没发生，版本还是旧的，连错误框都没有。

**原因**：`DoUpdate` 传的是 `/SILENT /NORESTART /CLOSEAPPLICATIONS`。
Inno 收到 `/CLOSEAPPLICATIONS` 会用 **Restart Manager** 去礼貌地关闭占用目标
文件的程序；而我们的客户端在 `OnFormClosing` 里 `cancel`（缩到托盘）——
RM 永远等不到关闭，静默模式下直接失败且不弹框。

**处理**：自动更新只传 `/SILENT /NORESTART`。关闭旧客户端由安装器的
`InitializeSetup` 调 `/stop` 负责（它会先 `RestoreDirect()` 还原系统代理，
直接 taskkill 会让用户装完就断网）。

**对照实验**（同机同包，这是定位的关键）：

| 参数 | 结果 |
|---|---|
| `/SILENT /NORESTART /CLOSEAPPLICATIONS` | 静默失败，版本不变 |
| `/SILENT /NORESTART /LOG=…` | `Installation process succeeded` + `[Run]` 自动启动 |

## 46. 用字符串替换改 `.iss` 会误伤注释里的段名

**现象**：给 `installer/ferry.iss` 加 `[InstallDelete]` 段，编译报
`Text is not inside a section`，行号指向文件头部的注释。

**原因**：文件头注释里有一句「…原生支持 `[Tasks]` 和 `[InstallDelete]`」以及
「`[Run]` 的 postinstall」，我的脚本用 `s.replace('[Run]', ...)` 找第一个匹配，

```python
lines = s.split('\n')
idx = next(i for i, ln in enumerate(lines) if ln.strip() == '[Run]')
lines[idx:idx] = new_section_lines
```

## 49. 每 3 秒重排表格 = 正在编辑的输入框被吃掉

**现象**：在「已登录的机器」里改备注，打一半，3 秒后输入框失去焦点、内容清空。

输入框因此丢焦点。

**处理**：重排前检查有没有正在编辑的备注：

```js
if (document.querySelector('.notecell.editing')) return;  // 数值更新照常，跳过排序
```

**教训**：轮询刷新要区分「更新数值」和「重建结构」。前者便宜且安全，后者会打断用户输入。

## 50. WinForms 在 per-monitor DPI 下算不出缩放因子

**现象**：150% 缩放的机器上，状态行的文字被右边的按钮压住、底部署名被裁半行；
但字体看起来并没有变小 —— 是控件没跟着放大。

**原因**：manifest 声明 `permonitorv2` 时，`Form.PerformAutoScale()` 执行的那一刻
还没确定窗口落在哪个显示器，`CurrentAutoScaleDimensions` 拿不到真实 DPI，
缩放因子算成 `1.0`。于是控件保持 96 DPI 的像素尺寸，而字体已经按系统 DPI
渲染完毕 → 字体比控件大。

**处理**：退到 **System DPI aware**（manifest `true` + `system`），
由 Windows 把整个窗口按比例位图放大；`AutoScaleMode` 改 `None` 避免二次缩放。
代价是非整数缩放（125%/150%）下字略微发虚，但绝不裁字。

**教训**：`AutoScaleMode.Dpi` 不是银弹。WinForms 要做对 per-monitor，
得全用 AutoSize/TableLayoutPanel 或自己处理 `WM_DPICHANGED` —— 那是重写界面的量级。

## 52. WMI `Win32_Process.Create` 不认「整个命令行被引号包住」

**现象**：提权重启 / 自动更新时调用

```csharp
Elevator.StartDetached("\"" + exe + "\"");
```

返回码 **9**（Path Not Found），新进程根本没起来。用户看到的是
「程序退出后再也没回来」。

**原因**：`Win32_Process.Create` 的 `CommandLine` 参数不是「一个可执行文件路径」，
而是一整条命令行。当整条命令行以引号开头时，WMI 会把它当成
「带引号的字符串」而不是「路径 + 参数」，于是找不到文件。

**处理**：走 cmd 让它自己拆引号：

```csharp
Elevator.StartDetached("cmd.exe /c start \"\" \"" + exe + "\"");
```

`start ""` 里那个空标题不能省 —— 省了的话 `start` 会把第一个带引号的
参数当成窗口标题，于是又变成「找不到文件」。

**教训**：`Process.Start(fileName, args)` 和「一整条命令行字符串」是两种语义，
不要混着用。

## 53. 自动更新失败三次，根因是三个叠加的低级错误

**现象**：点「更新」→ 选「是」→ 程序退出 → 再打开还是旧版本。
日志停在「发现新版本 x.y.z」之后，**一行都没有**。

**三个原因**（都在 `DoUpdate` 里）：

1. **整个方法跑在 UI 线程上**。`wc.DownloadFile()` 是同步的，界面直接冻住。
   用户看到的就是「点完就没了」；而且冻住期间任何 `MessageBox` 都画不出来，
   所以连错误提示都看不到。
2. **第一句又调了一次 `Api.Version()`**。`CheckUpdate` 明明已经拿到版本号了。
   而正在借网时系统代理指向 `127.0.0.1:10801`，这次请求可能超时；
   失败就 `if (!v.Ok) return;` —— 静默返回，界面上什么都不发生。
3. **结尾调 `RealQuit()`**。它在「正在借网」时会弹「当前正在借网，退出会恢复直连，
   确定吗？」，用户点「否」→ 程序留在原地，但 exe **已经被改名成 `.old` 并换成新版了**
   （半更新状态：进程跑的还是旧映像，磁盘上已经是新文件）。

**处理**：

- 版本号由 `CheckUpdate` 当参数传进来，不再重复请求
- 下载 / 改名 / 复制 / 启动全部丢进 `ThreadPool.QueueUserWorkItem`
- 成功后直接 `Environment.Exit(0)`，**不走 `RealQuit`**
- 每一步写 `[更新] xxx` 日志（`UpdateLog`），失败也写

**为什么之前三次都没修好**：我用「手动把 exe 复制过去、看到版本号变了」
当验收。那不是测试，是自欺。真实链路一次都没跑通。

## 55. 文字下半截被裁：不是 DPI 模式的问题，是控件高度写死

**现象**：不同用户都反馈「文字下面一半被遮挡」，缩放比例不同、裁掉的程度不同。
我先后改了三次 `dpiAware`（permonitorv2 → system）和 `AutoScaleMode`，**全都没用**。

**真正原因**：

```csharp
Theme.Text2:  l.AutoSize = false;
Row:          l.SetBounds(24, y, 430, 18);   // ← 高度写死 18px
```

字体是 pt 单位，**随系统 DPI 放大**。125% 下 8.5pt 中文单行需要 20px，
而控件只有 18px → 每行字下沿裁掉 2px。缩放比例越大裁得越多。

**怎么定位的**：写了个诊断程序，在真实 DPI 下遍历窗体里每个 Label，
对比「设定高度」和「实际需要高度」：

```
DPI = 120 (125%)
FSmall 8.5pt 单行高 = 20px
Row() 给的高度      = 18px

Text(前16字)        Width Height  需要   结论
渡口                 120     28    30   裁掉 2px
内网应急接入 · 断网时…   300     18    40   裁掉 22px
本地代理    未运行      430     18    20   裁掉 2px
```

改前 11 个控件被裁（2~22px），改后 **0 个**。

**处理**：

- Label / CheckBox 一律 `AutoSize = true` + `MaximumSize` 限宽
- 新增 `Theme.Place(l, x, y, w)`：只给位置和宽度，高度交给控件自己算
- 多行文字的 y 坐标按**上一项实际高度**累加，不再写死间距
- 卡片高度按内容撑开，下方控件按增量整体下移、窗口加高

**为什么不用 `TextRenderer.MeasureText` 自己算**：试过了，中文长句算不准。
`WordBreak` 依赖空格断行，中文没有空格 → 它认为一行放得下、返回单行高度，
而 Label 实际渲染会按字符折行。结果「按测量值给高度」依然被裁。
要量高度就用一个临时 Label 的 `PreferredHeight`。

## 56. AutoSize 的控件在还没有父容器时 `Height` 是 0

**现象**：改成累加式布局后，设置页的四个勾选项仍然叠在一起：

## 59. 更新后程序消失：新进程抢不到单实例锁

**现象**：点「更新」→ 选「是」→ 程序消失，**再也不出现**。没有任何错误框。

**根因**：启动新进程和退出旧进程的**顺序反了**。

```csharp
// 错误写法
StartDetached("cmd.exe /c start \"\" \"app.exe\"");   // ① 先起新进程
Thread.Sleep(400);
RestoreDirect(); _rt.Stop();                          // ② 借网时要停代理（几百 ms）
Environment.Exit(0);                                  // ③ 才退出
```

```
T+0ms     新进程启动（cmd /c start 有 200~500ms 开销）
T+0ms     旧进程还活着，持有 Local\FerryClient 互斥锁
T+300ms   新进程抢锁失败 → 以为「已有实例」→ 前置旧窗口 → 自己退出
T+400ms   旧进程 Exit → 窗口销毁
结果      两个都没了
```

**为什么「开着借网」时更容易复现**：`RestoreDirect()` + `_rt.Stop()` 要还原
系统代理、杀 mihomo、清路由，需要几百毫秒 —— 旧进程活得更久，新进程输掉
竞态的概率更高。不借网时旧进程退得快，偶尔能赢。

**修法**：

1. 先收拾干净（还原代理、停运行时），**再**安排重启
2. 延迟 2 秒再拉新进程：写一个 `ferry-relaunch.cmd`（`timeout /t 2` 后 `start`），
   用 WMI 起它（脱离 Job），然后自己 `Environment.Exit(0)`
3. 新进程带 `/allow-wait`：即使旧进程退得慢，它也会等锁而不是误判

**教训**：凡是「A 退出、B 接替」的场景，**B 必须等 A 真的退干净**。
判断「退干净」不能靠 `Sleep(固定值)` 猜，要么用互斥量/事件通知，
要么让 B 自己带重试等待（`/allow-wait` 那种）。

**这个 bug 藏了很久的原因**：它是个竞态 —— 有时能成、有时不能。
用户说「有时候可以」时，第一反应应该是「查竞态」，而不是「再改改看」。

## 60. `MinimumSize` 会让 `AutoSize` 的高度自适应失效

**现象**：「全局模式」按钮只剩边框、文字没了；多行提示压住下面几行。

**根因**：为了锁宽度，同时设了 `MinimumSize` 和 `MaximumSize`：

```csharp
l.MinimumSize = new Size(w, 0);   // ← 元凶
l.MaximumSize = new Size(w, 0);
l.AutoSize = true;
```

WinForms 里 `MinimumSize` 会**压制 AutoSize** —— 宽度锁死了，高度也跟着
锁在「设 MinimumSize 那一刻」的值上。于是 47 个字的提示只有 19px 高
（1 行），文字溢出边界盖住下面的控件。

诊断数据：

```
_lblDesc.Text   = [系统代理指向渡口，但本地代理端口没响应。点「停止并恢复直连」再重新开始。]
_lblDesc.Bounds = {X=0, Y=54, Width=477, Height=19}   ← 需要 4 行 76px
```

**修法**：不用 `AutoSize`，自己算高度（`Theme.AutoLabel`）：

```csharp
protected override void OnTextChanged(EventArgs e)
{
    base.OnTextChanged(e);
    Refit();     // 用临时 Label 量出真实高度再设回去
}
```

临时 Label 用 `AutoSize = true` + `MaximumSize`（**不设 MinimumSize**），
它的 `PreferredHeight` 和真实渲染完全一致。

**连带坑**：改完发现宽度没设 → AutoLabel 按上一次的宽度（100px）算成
6 行 114px，把卡片撑爆。**高度自适应依赖宽度**，布局时必须先定宽度再量高度。

**教训**：`MinimumSize` / `MaximumSize` / `AutoSize` 三者互相影响，
文档里没写清楚。凡是「自动尺寸不生效」的情况，先查有没有设 MinimumSize。

## 61. 界面验证不要占用用户的桌面：远端离屏渲染的三个坑

**背景**：用户明确要求「别在我这台电脑跳弹窗，想截图用 ssh 主机 10.113.66.6」。
起因是我为了看真实渲染，反复激活/前置他的窗口，还起了一堆测试进程。

**做法**：`tools/render-ui.ps1` —— 本地源码 → scp 到 10.113.66.6 →
远程用 csc 编一个 harness → `RenderTargetBitmap` 离屏渲染三个窗口 →
scp 回 PNG。全程不碰任何人的桌面。

**踩到的三个坑**（都写进了 `tools/ui-shot/shot.cs` 的注释）：

1. **`Show()` 在 Session 0 会失败**。SSH 登进去的是 `services` 会话（SessionId 0），
   没有交互桌面，创建 HWND 直接失败。所以只对 `Window.Content` 做
   `Measure` / `Arrange` 再渲染，不 Show。

2. **字体继承链断了**。`FontFamily` / `FontSize` / `Foreground` 是设在 `Window`
   上、由子元素继承的；离屏时 `Content` 不在窗口的视觉树里，继承不生效 → 用回
   默认 Segoe UI，中文行高偏小，底部按钮被算出画布外（第一版截图按钮就少了半截）。
   修法是渲染前把这三个属性显式设到根元素：
   ```csharp
   TextElement.SetFontFamily(root, w.FontFamily);
   TextElement.SetFontSize(root, w.FontSize);
   TextElement.SetForeground(root, w.Foreground);
   ```

3. **`root.DesiredSize` 不可靠**。窗口设了 `SizeToContent = Height` 之后，
   `DesiredSize` 拿到的是被约束过的值（446），而内容实际需要 482 —— 按它建画布，
   最后一行按钮必然被切。改成按子元素 `DesiredSize.Height` 累加，并按实际
   `TranslatePoint` 的底部再校正一次。

**顺带一个发版流程的漏洞（属于踩坑 53 的同类）**：
`/download-client` 发的是 `dist\渡口助手.exe`，不是安装包。发版时只传
`Ferry-Setup-*.exe` 的话，`version.json` 会说 1.0.1，但自动更新下下来的还是旧 exe。
第一次远端自检就撞上了：日志写着「服务端版本 = 1.0.1」，下下来是 `0.9.37.0`。
现在发版清单里两个文件都是必须项。

**教训**：验证环境要和生产环境分开。用户的电脑是生产环境，不是测试机；
一旦需要「占桌面」「弹窗」「抢焦点」，就该找另一台机器，而不是让用户忍着。

## 62. 激活令牌只存在安装目录里，卸载一次就没了

**现象**：用户反馈「卸载重启，或者更新，有时候还是会出现密钥丢失需要重新填」。

**根因**：令牌只在 `config.json`，而同目录的 `.bak` 也在安装目录里，安装器又写：

```
[UninstallDelete]
Type: filesandordirs; Name: "{app}"
```

「卸载 → 重装」= 目录连同配置一起消失。加上两个历史包袱，看起来就像「有时候丢、
有时候不丢」：

- 0.9.2 时代是 admin 安装，配置写在**执行提权的那个管理员账户**的
  `%LOCALAPPDATA%\Ferry` 下；换到 per-user 后读不到；
- 装到新目录时安装器写的是空 token 的新配置。

**修法**（三层，任意一层活下来就能自愈）：

1. `Cfg.Save` 每次额外写 `%APPDATA%\Ferry\config.backup.json`（不在卸载范围）；
2. 启动时 `Cfg.RecoverFromRoamingBackup`：主配置没 token 而备份有 → 复制回来；
3. 安装器 `ssPostInstall` 也查这份备份（卸载后直接重装、客户端还没启动的情况）。

**两个反直觉的边界**（不写清楚下次一定改错）：

- **只在有 token 时写备份**。否则「新装、还没激活」的空配置会把好备份冲掉。
- **主配置的 `.bak` 也要保护**：要写的内容没有 token、旧 `.bak` 有 → 保留旧的。
  否则会出现这条链路：配置读坏 → 内存里是默认值 → 用户随手点了个保存 →
  唯一能用的备份被空配置覆盖 → 只能重新要密钥。
- 反过来，`Cfg.Load` **不因「token 为空」就退回 `.bak`**：那是用户主动清空的语义，
  自动恢复会让人以为「清不掉」。真正兜底放在启动时那一步（会写日志）。

**教训**：凡是「凭证」类数据，存储位置一定要选**不在卸载/升级范围内**的目录，
并且至少两处。只放在安装目录里的东西，卸载就是删除。

**验证**：`tools/verify-cfg-recovery.ps1`（16 项，含「更新后配置逐字节不变」）。

## 63. 更新时「目录里暂时没有 exe」的窗口，足以让程序永久起不来

**现象**：自动更新历史上反复出「点完是就消失了」，用户只能重装。

**根因之一**（除 Job Object 那几条之外）：更新顺序是

```
rename(渡口助手.exe → 渡口助手.exe.old)   ← 这一步之后目录里没有 exe
copy(下载的 tmp → 渡口助手.exe)          ← 几百 ms ~ 几秒
```

这两步之间进程被杀 / 断电 / 杀软拦截 / 磁盘满，就只剩一个 `.old`。
快捷方式指向的 exe 不存在，用户双击没反应，**而且没有任何东西能把它救回来**
（进程都起不来，谈不上启动自愈）。

**修法**：把「落新文件」提到改名之前，用两次 rename 收尾：

```
copy(tmp → 渡口助手.exe.new)          ← 失败：exe 还在，直接报错
rename(渡口助手.exe → .old)            ← 微秒级
rename(.new → 渡口助手.exe)            ← 微秒级，失败就 rename 回去
```

同卷 rename 是 NTFS 原子操作，窗口从「秒级」压到「微秒级」，而且任何一步失败
磁盘上都还有一份完整可执行的 exe。

**顺带一并修的两处**：

- `UnhandledException` 之前挂在「拿到单实例锁之后」，导致启动早期（读配置、
  恢复备份、WPF 初始化）的崩溃**一个字节都不写日志**。这次测试撞上几次
  「进程 exit 0、日志空」，完全无法判断是锁冲突还是崩溃 —— 现在挪到 `Main`
  第一行，并补了 `启动：参数 [...]`、`拿到单实例锁`、`进入消息循环`、`进程退出`。
- `.old` 在「更新完立刻重启」时可能还被系统锁着，删不掉就残留在目录里。
  现在 3 秒后重试一次。

**教训**：凡是「替换正在运行的文件」，顺序要设计成**任何一刻磁盘上都有可执行版本**。
不是「加个 try/catch 回滚」就够了 —— 回滚代码在进程被强杀时根本不会执行。

**验证**：借网状态下跑真实 `/auto-update`（1.0.2 → 1.0.3），日志逐行见 CHANGELOG `v0.14.2`。

## 64. 「验证激活恢复」删了用户的配置 —— 他直接断网四十分钟

**过程**：为了验证「服务端按 IP 恢复激活」，我把用户机器上的
`config.json`、`config.json.bak`、`%APPDATA%\Ferry\config.backup.json`
三份全删了（想模拟「卸载重装」）。

**后果**：
1. 令牌没了，客户端变未激活；而 `portalUrl` 也是空的，激活请求拿着空 URL
   去发 → `无效的 URI：未能确定 URI 的格式`。
2. 这台机器**本来就是靠渡口借网上网的**。我随后杀进程 / 重启客户端，
   代理和 TUN 一起消失 —— 他连「去门户重新要密钥」都做不到。
3. 恢复只能用我自己留下的临时备份（`/tmp/cfg.bak.json`），纯属侥幸。

**教训（两条，都是硬规则）**：

- **程序不许删用户的配置**，只做「没有就补」。卸载也只清安装目录，
  漫游目录里的激活备份要留 —— 它比「卸载干净」重要得多。
- **在用户的机器上重启客户端 = 断他的网**。任何需要重启的验证都要去
  测试机（10.113.66.6）。这条在「别在我电脑跳弹窗」之后就该想到，但没推到底。

**顺带修掉的产品能力**：服务端 `/api/config?with_token=1` 现在可以按**来源 IP**
下发令牌（只允许查自己那一份），客户端在「本地没有 token」时调它，
于是卸载重装 / 配置被清之后不用再找管理员要密钥。默认不带 `with_token`，
安装包仍然不含凭据。

## 65. 在 SSH 会话里启的服务，SSH 一断就被回收 —— 所有人断网

**过程**：改完 `ferry-socks5-server.py`（把 `--clash-proxy` 默认值从 auto 改成 off），
在 SSH 会话里：

```powershell
Stop-Process -Id <旧 python> -Force
Start-Process cmd.exe -ArgumentList '/c', 'run-relay.cmd' -WindowStyle Hidden
```

脚本返回「已启动」，但 `Get-NetTCPConnection -LocalPort 1080` 是 **False** ——
服务根本没起来。用户（以及所有借网的人）当场断网。

**根因**：客户端建过的 Job Object 带 `KILL_ON_JOB_CLOSE`（踩坑 44 记的就是它）。
SSH 会话结束时，会话里起的子进程被整组回收。**「脚本执行成功」不等于「进程活着」。**

**正确做法**：

```powershell
schtasks /create /tn FerrySocks5 /tr "cmd /c C:\...
un-relay.cmd" /sc onstart /ru SYSTEM /rl highest /f
schtasks /run /tn FerrySocks5
# 必须验证，不能只看命令返回
netstat -an | findstr ":1080 " | findstr LISTENING
```

**教训**：

- 远端服务的**启动方式**和代码同等重要。一个「改一行默认值」的部署，因为进程归属错了，
  造成的影响比代码 bug 大得多。
- 「我执行了启动命令」≠「服务在跑」。**必须用端口/日志确认**，而且确认要在
  **新会话**里做（同一会话里看到的东西可能是自己刚起的、马上要死的）。
- 动远端前先问一句：现在有谁在用？停多久？这次是凌晨一点半停的，用户正打着游戏。

**事故后的恢复路径**（值得记）：用户已经不在校园网内、SSH 也不通，
最后是靠**他能用 UU 远程连上那台机**，手动跑 `schtasks` 拉回来的。
所以远端机器至少要留**一条与业务网络无关的带外通道**（UU/向日葵/远程桌面都行）。

## 66. 「自动把节点写进用户的 Clash 配置」—— 试了四版，全废

**背景**：渡口借网时会接管系统代理，和用户自己的 Clash 抢同一个位置。
1.0.9 起我做的方案是：检测到被占用 → 退成「节点模式」，然后**帮用户把渡口
作为一个 SOCKS5 节点写进他的 Clash 配置**。

**四版的过程**：

| 版本 | 写哪里 | 结果 |
|---|---|---|
| 1.0.9 | Verge 系 `profiles\Merge.yaml` | Verge 用户 OK，CFW 用户「点了没反应」 |
| 1.0.11 | CFW `parsers\ferry.js` + `profiles.yaml` | 猜的机制，CFW 根本没有这种设计 |
| 1.0.12 | CFW `config.yaml` + `cfw-settings.yaml` 的 parsers | 部分用户仍不生效 |
| 1.0.13 | 全部砍掉，只显示一段可复制的 YAML | 终于不再有人来问 |

**为什么必然失败**：

- Clash for Windows 有**绿色版**（解压即用），配置目录根本不在 `%USERPROFILE%\.config\clash`；
- Verge / Rev / Nyanpasu / CFW 的存储位置和格式**各不相同**，改一个就要适配一轮；
- 用户装的是哪个、哪个版本、是不是汉化版，我全都不知道；
- 最要命的是：**写错了会毁掉人家的翻墙配置**。那比「不做」严重得多。

**更根本的错误**：这条路解决的是错的问题。用户既然装了 Clash，他要的是
「借网之后还能翻墙」，不是「在 Clash 里多一个节点」。后来改成渡口自己分流
（国内走渡口、境外交给他本机的代理），用户**什么都不用配** —— 这才是正解。

**教训**：

> 当你的方案需要「适配每个用户的第三方软件」时，先停下来问：
> 我是不是在绕弯？有没有可能把这件事变成「我不需要知道他用什么」？

**判据（下次直接用）**：如果一个功能的实现需要枚举用户可能装了什么软件、
它们的配置文件在哪、格式是什么 —— 这个功能大概率不该这么做。

**后遗症（2026-10-27 追加，比上面更严重）**：

那次写进去的 `prepend-rules: [GEOIP,CN,国内出口]` 在**四个版本之后还在生效**。
它排在所有规则最前面，把国内流量全劫持到渡口端口；渡口没借网时端口是空的
→ 用户报「只能访问外网，国内网站全打不开」。外网能开是因为走机场节点，
不受这条规则影响，所以现象看起来像「只能上外网」。

**这才是「写别人配置文件」真正的代价**：不只是「可能写错」，而是
**写对了也会留下后遗症，而且用户完全不知道是国内哪一环坏了**。
补救还得靠客户端启动时主动去删（`ClashCleanup.CleanLegacy`）。

**追加判据**：就算你确信自己写对了，也要问一句 ——
**这段配置如果一直留着、而我的程序三个月后不再管它，会发生什么？**
如果答案是「会坏」，那就不要写。

## 67. 「请在主界面点那个按钮」—— 让用户多走一步，还可能是死路

**现象**：设置窗里点「检查更新」，发现新版本后弹框说
「请在主界面点「更新 1.0.13」按钮完成更新」。

**两个问题**：

1. 用户已经在更新流程里了，却被要求关窗、切窗口、找按钮、再点一次；
2. **那个按钮不一定在**。主界面的「更新」按钮只在「检查更新跑过一次并发现新版」
   时才显示。从设置里知道有新版，回主界面很可能什么都看不到，以为没更新。

**修法**：把更新能力直接传进设置窗（`Action<string> onUpdate` = 主窗口的
`DoUpdate`），点「是」就开始更新。更新本来就在后台线程跑，窗口关掉不影响。

**教训**：

> 任何「请去另一个界面点某个按钮」的提示，都是一个待修的 bug。
> 正确做法是把那个能力传过来，而不是把用户送过去。

**连带发现的两个小坑**（顺手一起修了）：

- 更新前没有落盘设置 —— 更新会让进程退出、新版重读配置，用户刚改的选项就丢了；
- 连不上门户时只说「拿不到版本信息」，用户无法判断是自己网的问题还是服务端的问题。

## 68. 「按目标决定去向」的逻辑，必须验场景矩阵

分流（国内走渡口 / 境外交给用户代理）写完时，我只验了「国内通、境外通」两条。
后来逐个场景验，才发现三个真 bug：

| 场景 | 原来的行为 | 问题 |
|---|---|---|
| 没有本机代理 | 直接传原始域名给上游 | 远端 DNS 被污染，等于让它拿假地址 |
| **节点模式** | 仍然按「境外」送回本机代理 | **成环**：Clash → 渡口 → Clash |
| 代理挂掉 | 每条连接写一行日志 | 浏览器一开几十行，几分钟几 MB，真错误被冲掉 |

**为什么容易漏**：这类逻辑的 happy path（有代理、代理健康、目标正常）
恰好是开发时手边唯一的环境。异常分支只有把场景列出来才会想到。

**做法**：写一张「模式 × 目标 × 上游健康状态」的表，逐格验：

```
                 有本机代理          没有本机代理
接管模式      国内→渡口 / 境外→代理    全走渡口（不抛异常）
节点模式      全走渡口（不成环）       全走渡口
代理中途挂掉  境外回落渡口（不抛异常）  ——
```

**教训**：

> 凡是「根据条件决定走哪条路」的代码，验收标准不是「主路径能通」，
> 而是「每一格都有明确且不致命的行为」。

工具：`tools/verify-scenarios.cs`（5 个场景）、`tools/verify-split.cs`（基础分流）。

## 69. 「本地解析域名」的前提是「本地解析结果是真的」—— fake-ip 打破了这个前提

**现象**：用户升级后「开启借网反而上不了网」，国内网站全部打不开。

**根因链**：

```
TUN 启用 → mihomo 用 fake-ip 接管系统 DNS（198.18.0.0/15）
        → 任何域名都解析成 198.18.x.x
        → IsDomestic 拿这个假 IP 查 APNIC 的 CN 段表
        → 当然不在里面 → 判成「境外」
        → PreferIp 把 198.18.x.x 传给远端
        → 远端连一个不存在的地址 → 失败
```

1.0.13 之前是「直接把域名交给上游」，所以没事；我加了「本地解析成 IP 再传」
（为了绕开远端 DNS 污染）之后，才和 fake-ip 撞上。

**教训**：

> 凡是拿 DNS 结果做判断的代码，都要先问：**这个结果可能是 fake-ip 吗？**

TUN 类工具（mihomo / Clash / sing-box）在 `enhanced-mode: fake-ip` 下，
DNS 返回的是**内部编号**，不是地址。识别方式：`198.18.0.0/15`。
见到它应该：
- 别拿它做地理判断（它不是真实地址）
- 别把它传给上游（上游连不上内部编号）
- 保留原域名，让懂这层的那一方（TUN）自己解析

**同一个 bug 的第二面**：节点模式下还启用了 TUN。

```
16:42:47 系统代理已由其它程序管理，本次不接管（只提供本地端口）   ← 节点模式
16:42:49 TUN 已启用（网卡 FerryTun）—— 全局接管生效                ← 又全接管了
```

这两句在同一个日志里，语义直接矛盾。节点模式 = 「我只开一个端口」，
TUN = 「我抢默认路由」。同时启用会和用户本来开着的 Clash/加速器 TUN 抢路由，
而且让「不接管系统代理」变成谎话。新增 `AllowTun`，节点模式设 false。

**元教训**：两个「接管全部流量」的机制不能同时开。设计模式开关时，
要把「这个模式会不会抢全局资源」列出来，逐个排除冲突。

## 70. 安装包漏打资源文件，功能会「静默降级」而不是报错

**现象**：用户反馈「托盘没有图标」。

**根因**：`MainWindow.BuildTray()` 是这么写的：

```csharp
var ico = Path.Combine(_appDir, "app.ico");
_tray.Icon = File.Exists(ico) ? new System.Drawing.Icon(ico) : System.Drawing.SystemIcons.Application;
```

而 `installer/ferry.iss` 的 `[Files]` 里**从来没有 `app.ico`** —— 仓库里有
`ferry-client/app.ico`，但没打进安装包。所以 `File.Exists` 永远是 false，
永远退回系统默认图标。

**为什么难发现**：这段代码有 try/catch、有 fallback，**不报错、不写日志**。
功能「降级」而不是「失效」，没人会去查。

**教训**：

> 带 fallback 的代码会掩盖资源缺失。加资源时必须在**安装包**里验证，
> 而不是在开发目录里验证 —— 开发目录里文件都在，看不出问题。

**验证方法**：装完之后直接列安装目录，比对「代码里会读的文件」是否都在。


## 71. `SetBusy` 这类防重入锁，会把「顺序调两个异步方法」变成静默失败

**现象**：点「关闭全局模式」只回到直连、没有重启；再点「开启全局模式」也没反应。

**代码**：

```csharp
if (running) { DoStop(); DoStart(); return; }   // 看起来天经地义

void DoStop() {
    if (_busy) return;      // ← 第一行
    SetBusy(true);
    ThreadPool.QueueUserWorkItem(...);   // 后台做完才 SetBusy(false)
}
```

**执行顺序**：

```
DoStop()  → _busy = true，起后台线程，立刻返回
DoStart() → 立刻进来，_busy 还是 true → return，什么都不做
```

**为什么特别难查**：

- 不报错、不写日志、界面也没有任何提示；
- 单看 `DoStop(); DoStart();` 这一行，读一百遍也不会觉得有问题；
- 真正的问题在 `DoStop` 的**第一行**，隔着 60 行代码。

**修法**：用标志 + 回调衔接：

```csharp
_pendingRestart = true;
DoStop();       // 它完成后在 UI 回调里看标志，自己调 DoStart()
```

**教训**：

> 凡是「先停再起」「先切 A 再切 B」的地方，都要问一句：
> **这两个方法是不是异步的？有没有防重入锁？**

防重入锁 + 顺序调用 = 第二个被静默吞掉。这类 bug 只在**连续操作**时出现，
单步测试永远发现不了 —— 验收时必须连点两下。

**顺带修的第二个 bug（同一个功能的另一面）**：

节点模式下 `AllowTun=false`（避免和 Clash 抢 TUN），但界面上仍然显示
「已开启」/「正在启用…」，而大状态又写「全局接管未启用」——三处打架。

根因是**「用户的意图」和「当前能不能做到」混在一处显示**。
修法是把「点开启」当成明确意图（`_forceTakeover`），接管系统代理；
关掉时让位回去。

**元教训**：一个开关的状态要分清三层 —— 用户意图、实际状态、能否做到。
三个都显示在同一行，必然自相矛盾。


## 69. 安装包被「应用控制策略」拦下：Inno 天生要写临时目录

**现象**（用户反馈，不止一台机器）：

```
无法执行临时目录中的文件。安装程序已中止。
错误 4551: 应用程序控制策略已阻止此文件。
```

**不是杀软报毒，也不是文件损坏**，是 Windows 的智能应用控制（SAC）/
WDAC / AppLocker 禁止「从 `%TEMP%` 执行程序」。

**为什么躲不掉**：Inno Setup 的安装包结构是
`Setup.exe`（SetupLdr，很小的引导器）+ 压缩的 `setup.tmp`。
运行时引导器把 `setup.tmp` 解压到 `%TEMP%\is-XXXXX.tmp\` 再 CreateProcess 它。
**只要用 Inno 的默认结构，就一定会从临时目录执行程序。**

**试过并回退的修法**：`UseSetupLdr=no`。

- 它确实能绕开临时目录（Setup.exe 本身就是安装程序）；
- 但会把单文件拆成 `Setup.exe` + `Setup-0.bin` + `Setup-1.bin` 三个文件
  （17.7MB 的包变成 4.4MB + 23KB + 15.6MB），分发反而更麻烦；
- 而且用户更容易下错、只下一个文件导致安装失败。

**最终做法**：保留单文件安装包，**另外**发一个免安装 ZIP
（`dist/Ferry-Portable-<ver>.zip`，门户 `/download-portable`）。
解压到任意目录双击即用，完全不经过 `%TEMP%`。

**教训**：

- 「装不上」的报错要先分清是**杀软**、**系统策略**还是**文件损坏**。
  这次的文案（「应用程序控制策略已阻止」）已经说得非常明白，
  但第一反应还是容易归到杀软头上，方向会错。
- 有些限制**改不了**（Inno 的结构是设计如此），这时应该**多给一条不依赖它的路**，
  而不是硬改那个改不动的东西。
- 绿色包不是妥协：它天然规避了「安装器写临时目录」「写注册表」「要管理员」
  三件事，对「只想用一下」的用户反而更省事。

## 70. 全局模式的开关判断错了：用「实际状态」而不是「用户意图」

**现象**：TUN 起不来时（另一个 TUN 在抢路由），界面显示
`全局模式 未启用：另一个 TUN 正在接管`，按钮写着 `关闭全局模式`，
但**点一次就重启一次借网，永远关不掉**。

**根因**：

```csharp
bool tunUp = running && _rt.TunRunning;
if (tunUp) { /* 关闭分支 */ } else { /* 开启分支 */ }
```

按钮文字是按 `_cfg.UseTun`（用户意图）显示的 —— 用户勾了全局模式，
所以文字是「关闭」；但点击处理按 `tunUp`（TUN 是否真的在跑）判断 ——
TUN 没跑，于是落进「开启」分支，把 `_cfg.UseTun` 又设成 true，然后重启。

**修法**：开关的判据统一用**用户意图**（`_cfg.UseTun`）。
界面写「关闭」就真的关；TUN 起没起来是另一回事，由状态文案单独说明。

**这是同一个坑的第三次**（第一次是「全局模式」复选框与主界面开关不同步，
第二次是设置窗与主窗口各自持有一份状态）。**开关类控件必须只有一个来源**：
用户意图存配置，实际运行状态只用于显示。

**验收标准**：不只是「能开」和「能关」，而是**四种组合都要走一遍**：

| 用户意图 | 实际状态 | 按钮应显示 | 点击后应发生 |
|---|---|---|---|
| 开 | 真的开着 | 关闭全局模式 | 关掉并重连 |
| 开 | 起不来 | 关闭全局模式 | 关掉（不是再开一次）|
| 关 | 没开 | 开启全局模式 | 开启 |
| 关 | 残留状态 | 开启全局模式 | 开启 |

## 71. 把「TUN 存在」当成「不需要分流」，境外流量全成了 502

**现象**：用户开 Clash（节点延迟 80~350ms 全绿）+ 开渡口借网 →
境外网站全部打不开，但 Clash 自己测速正常。

**实测对照**（同一台机器、同一时刻）：

```
via ferry  baidu  -> 200
via ferry  google -> 502 网关错误
via clash  baidu  -> 200
via clash  google -> 200
```

一句话：**渡口出口到不了境外**（大陆联通 + DNS 污染 + 部分 IP 不可达）。
所以只要有一处把境外流量送进渡口，用户看到的就是「借网了反而上不了外网」。

**根因**：两处代码，同一个思路错误。

```csharp
// FerryRuntime.cs:210（1.0.16 加的）
int clashPort = (AllowSplit && !_cfg.UseTun) ? DetectLocalProxy(...) : 0;
```

当时的注释写的是「TUN 模式下不分流：mihomo 自己已经有分流规则」。
**但那时 mihomo 的规则是 `MATCH,ferry`** —— 所谓「分好流」其实是「全走渡口」。
于是勾了全局模式，境外流量双保险地送进渡口。

**这个错误值得单独记一笔，因为它的形状很常见**：
一个条件写下去的时候是对的（当时 TUN 规则确实有分流），
后来 TUN 规则被简化成 `MATCH,ferry`，这个条件就变成了「关掉分流」。
**两处配合的逻辑，改了一处必须回头看另一处的注释还成不成立。**

**修法**：TUN 层也做分流，两层分工。

| 层 | 国内 | 境外 |
|---|---|---|
| TUN（mihomo 规则） | `RULE-SET,cn` → ferry | `MATCH` → `clash-local` (127.0.0.1:7897) |
| 本地代理 | `IsDomestic` → 渡口 | `ConnectSmart` → 本机 Clash |

**三个必须一起做的细节**：

1. **不能用 `GEOIP,CN`**。它要下载 `geoip.metadb`：

   ```
   can't download MMDB: Get "https://github.com/MetaCubeX/meta-rules-dat/...": EOF
   ```

   借网场景（校园网禁网）下必然失败，规则加载不了 → mihomo 拒绝启动 →
   TUN 起不来 → 用户直接断网。**凡是「需要联网才能加载的规则」，
   在「没有网才用它」的软件里都是错的。**
   改用 `rule-providers` + `type: file`，客户端启动时自己生成。

2. **必须排除翻墙客户端自己的出站**（`PROCESS-NAME` → DIRECT），
   否则 `TUN 抓走 → 判境外 → 交给 Clash → Clash 连机场又被抓走` 成环。
   mihomo 支持 `PROCESS-NAME` （本机实测 `Mihomo Meta v1.19.32`）。

3. **/16 位图有已知偏差**：APNIC 把 `1.1.0.0/16` 的大半分给了 CN，
   于是 `1.1.1.1`（Cloudflare DNS）被判成国内。在 `RULE-SET,cn` **之前**
   加几条更细的 `IP-CIDR,...,overseas` 例外即可。
   **粒度不够时不要提高整张表的精度，加例外更快也更安全。**

**验收方式**：不能只看「配置生成了」，要
① 断言规则顺序（例外在 RULE-SET 前、MATCH 在最后）
② 跑 `mihomo -t -f <配置>`，让它自己说 `test is successful`。

## 72. fake-ip 是占位符，不是地址 —— 拿它做地理判断等于把半个互联网判错

**现象**（1.0.21 上线后）：

> 为什么感觉网速明显变慢了，或者加载有点慢，不只是外网，国内网页也是

日志满屏同一句：

```
国内目标连不上，改走本机代理：www.google.com
国内目标连不上，改走本机代理：encrypted-tbn0.gstatic.com
国内目标连不上，改走本机代理：chatgpt.com
```

**每个境外域名都被判成国内**：先撞渡口（等超时）→ 失败 → 再走 Clash。
一个页面几十条连接，每条白等一次超时。国内网页也慢，因为页面里嵌了大量
境外资源（字体、统计、CDN）。

**根因**：

```csharp
// IsDomestic
foreach (var a in addrs)
    if (IsFakeIp(a) || CnIpRanges.Contains(a)) return true;
```

TUN 开着 `enhanced-mode: fake-ip`（198.18.0.0/16），系统 DNS 被 mihomo 接管，
任何域名都解析成 198.18.x.x。`IsFakeIp` 于是把所有域名都判成「国内」。

**`IsFakeIp` 本身是对的，错在把它的结论当成「国内」**。它只说明
「这个地址是本机 TUN 编出来的」，没有任何地理信息 —— 判成国内和判成境外
都是瞎猜，但**猜错的代价不对称**：猜国内 → 必定超时一次；猜境外 → 只是
多绕一跳（Clash 会自己判）。所以拿不准时一律选境外。

**连带的两处同源错误**：

1. **在 TUN 层按 IP 分流**（`RULE-SET,cn` 1151 条）。fake-ip 下域名进 TUN 时
   是 198.18.x.x，要匹配 IP-CIDR 就得先解析 —— **每个新域名多一次 DNS 查询**，
   而且用的是国内 DNS，墙外域名拿到的是污染地址，判定本身就错。
2. **`PreferIp` 用在了境外分支**。国内 DNS 解析墙外域名只会给污染地址，
   传给 Clash 就等于让它去连一个假 IP（而 Clash 自己有干净的解析）。

**修法**（一句话：分流只在一个地方做，且那一层必须拿得到域名）：

| 层 | 做什么 |
|---|---|
| TUN | 只转发。`PROCESS-NAME,<翻墙客户端>` → DIRECT（防环），其余 `MATCH,ferry` |
| 本地代理 | 唯一的分流点：国内 → 渡口（传 IP），境外 → Clash（**传域名**） |

配套：DNS 结果缓存（成功 300 秒 / 失败 30 秒）。分流是**每条连接**都要判的，
没有缓存等于每条连接发一次 DNS 查询。

**两条通用教训**：

- **「特判」写进判断条件之前，先问它到底提供了什么信息**。`IsFakeIp` 提供的是
  「这是本机编的地址」，把它当成「是国内」，等于用「不知道」推出「知道」。
- **同一个判断不要在两层各做一次**。两层都判 → 两套 DNS → 结论还可能不一致，
  排查时看到的就是「日志说走 A，实际走了 B」。

## 73. TUN 劫持着 53，客户端就再也拿不到真实 DNS 结果

**现象**（1.0.22 的日志）：

```
国内目标连不上，改走本机代理：223.5.5.5
国内目标连不上，改走本机代理：114.28.148.16
本机代理连不上，改走渡口：m701.music.126.net      ← 网易云音乐，纯国内
本机代理连不上，改走渡口：gateway.ooz.cn
```

两类错判，方向相反，日志里就是「转来转去」。

**根因**：1.0.22 的修法是「过滤 fake-ip，再用 223.5.5.5 重新解析」。但：

```
tun.dns-hijack: any:53
  → 客户端自己发的 UDP DNS（目标 223.5.5.5:53）
  → 进 TUN → mihomo 接管 → 返回 198.18.x.x（fake-ip）
  → 过滤掉 → 空 → 判「境外」
```

**只要 TUN 劫持着 53 端口，「本地解析出真实 IP」这条路就被堵死了。**
改 ResolveLocal 的过滤规则、换 DNS 服务器、加超时，全都没用 ——
问题不在解析逻辑，在于**根本没有真实答案可拿**。

**修法**：域名按域名判，不碰 DNS。

- IP 字面量 → 查 APNIC 段表（准确，且不需要解析）
- 域名 → 查内置后缀表（`.cn` + 常见国内站点/CDN），纯字符串比较，微秒级

**表只收「确定是国内」的**，因为判错代价不对称：

| 判错方向 | 后果 |
|---|---|
| 国内 → 境外 | 交给用户 Clash，它的 GEOIP 规则走直连，**能通**，多一跳 |
| 境外 → 国内 | 走借网出口，**必然打不开**（出口到不了境外） |

**顺带发现的**：出口探测用 `myip.ipip.net`，它被判境外时会交给 Clash，
于是界面显示的「出口 IP」其实是用户自己 Clash 的出口（这次显示成电信
116.23.158.149，而真实借网出口是联通 218.107.0.47）。**任何「探测自己状态」
的请求，都必须走得通那条确定的路**，否则显示的是别人的状态。

**教训**：

- 判断「我在哪一层」比判断「逻辑对不对」更重要。这一路改了三版
  （1.0.21 拿 fake-ip 当国内 → 1.0.22 过滤 fake-ip 后重新解析 →
  1.0.23 干脆不解析），每版都「逻辑正确」，但只有最后一版成立的
  原因是：前两版都假设「我能拿到真实 DNS」，而这个假设被 TUN 否掉了。
- **一次误判不要紧，错误方向要选代价小的那一侧**。上面那张表应该在写
  第一行代码之前就画出来。
