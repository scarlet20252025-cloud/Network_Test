# 分流架构：一个出口、两条路、三个决策点

> 这份文档记录的是**为什么这么设计**，不是**怎么写的**。代码会变，前提不会。
> 如果哪天要动分流逻辑，先读完这一页，再看 `ferry-client/src/Proxy.cs` 和 `TunMode.cs`。
>
> 最后更新：1.0.24（2026-10-27）

---

## 一、要解决的问题

渡口是**借网**工具：用户被校园网禁网时，借一台能出网的内网主机（pcs）当出口。

但它同时要让用户**自己的翻墙工具继续工作**。这两件事的目标是冲突的：

| | 渡口出口（pcs） | 用户自己的 Clash |
|---|---|---|
| 国内网站 | ✅ 通 | ✅ 通（直连） |
| 境外网站 | ❌ **打不开**（实测：大陆联通出口 + DNS 污染 + 部分 IP 层不可达） | ✅ 通（走机场） |

所以必须**按目标分流**：

```
国内  → 渡口出口（它是为了这个存在的）
境外  → 用户自己的 Clash（渡口不提供翻墙能力，也不该提供）
```

这条边界同时是**合规边界**：渡口只做「借网到国内」，境外流量由用户自己的
机场账号承担。所以服务端 `--clash-proxy` 从 1.0.8 起一直是 `off`。

## 二、三个决策点，各管一段

```
应用程序
   │
   │  ① DNS：TUN 模式下被 mihomo 劫持（dns-hijack: any:53）
   │     所有域名解析成 fake-ip（198.18.x.x）
   ▼
TUN 网卡（FerryTun，mihomo 接管默认路由）
   │
   │  ② mihomo 规则（这一层只看「谁在连」，不看「连哪里」）
   │     翻墙客户端进程  → DIRECT   （关键：否则成环）
   │     内网/回环 IP    → DIRECT
   │     其余            → ferry（本地代理 127.0.0.1:10801）
   ▼
本地代理（ProxyServer，混合端口 10801）
   │
   │  ③ 这里是**唯一**的分流决策点
   │     IP 目标    → 查 APNIC 段表
   │     域名目标  → 查内置后缀表
   ▼
┌─────────────┴─────────────┐
│ 判国内                     │ 判境外
▼                            ▼
渡口（pcs:1080 SOCKS5）    用户 Clash（127.0.0.1:7897）
→ 大陆出口                 → 机场节点
```

### 各层职责（不要混）

| 层 | 只做一件事 | 不做什么 |
|---|---|---|
| TUN（mihomo） | 决定**哪些流量进隧道** | 不判国内外、不解析域名 |
| 本地代理 | 决定**每条连接走哪个上游** | 不接管系统路由 |
| 上游 | 只负责转发 | 不做判定 |

**为什么不让 mihomo 层直接按 IP 分流？** 见第四节「fake-ip 的硬约束」——
那一层拿不到真实 IP，也拿不到干净的 DNS。

## 三、判定规则（唯一的真相表）

| 目标形式 | 判定方式 | 结果 | 依据 |
|---|---|---|---|
| IPv4 字面量 | `CnIpRanges.Contains()` | 在表内 → 国内 | APNIC 权威 CN 段表（/16 位图，5933 段） |
| IPv4 私网 / 回环 / CGNAT | 同上（表内已含） | 国内 → 直连 | 内网地址不该出网 |
| **fake-ip（198.18.0.0/15）** | 特判 | **境外** | 占位符，不含任何地理信息 |
| 域名，`.cn` 结尾 | 后缀 | 国内 | 国家顶级域 |
| 域名，命中后缀表 | 后缀 | 国内 | 内置约 130 条（头部站点 + CDN） |
| 域名，其余 | — | **境外** | 见下「代价不对称」 |
| IPv6 | — | 境外 | TUN 里 `ipv6: false`，实际不会出现 |

### 为什么判错时一律往「境外」错

| 判错方向 | 实际后果 |
|---|---|
| 国内域名 → 判境外 | 交给用户的 Clash，它的 GEOIP 规则会走**直连**。**能通**，只是多一跳（本地环回，微秒级） |
| 境外域名 → 判国内 | 走渡口出口。**必然打不开**（出口到不了境外），而且要多等一次超时 |

**这张表应该在写第一行分流代码之前就画出来。** 这个项目前后错了三次，
每次都是因为没先想清楚「错在哪一侧更贵」。

## 四、三条硬约束（违反任何一条都会退回错误状态）

### 约束 1：TUN 模式下，客户端拿不到真实 DNS

`tun.dns-hijack: any:53` + `dns.enhanced-mode: fake-ip` 意味着：

```
客户端问系统 DNS            → mihomo 接管 → 198.18.x.x
客户端自己发 UDP 到 223.5.5.5 → 仍然进 TUN → mihomo 接管 → 198.18.x.x
```

**只要 TUN 劫持着 53，「本地解析出真实 IP 再判断」这条路就是死的。**
换个 DNS 服务器、加超时、过滤 fake-ip —— 全都没用，问题不在解析逻辑，
在于**根本没有真实答案可拿**。

（正因如此，域名判定改成纯字符串后缀表，一个 DNS 包都不发。）

### 约束 2：翻墙客户端自己的出站必须放行，否则成环

```
用户请求 → TUN 抓走 → 判境外 → 交给 Clash
                                 ↓
                         Clash 去连机场节点 → 又被 TUN 抓走 → 再交给 Clash …
```

所以 mihomo 规则里必须有 `PROCESS-NAME` 例外。**1.0.31 起无条件写入** ——
以前是「启动 TUN 那一刻检测到本机 Clash 才写」，用户先起渡口再起 Clash
就永远没有这条保险（踩坑 74）：


```yaml
- PROCESS-NAME,clash-verge.exe,DIRECT
- PROCESS-NAME,verge-mihomo.exe,DIRECT
- PROCESS-NAME,Clash for Windows.exe,DIRECT
- PROCESS-NAME,v2ray.exe,DIRECT
- PROCESS-NAME,sing-box.exe,DIRECT      # 等 9 条
```

### 约束 3：分流只能在一个地方做

两层各判一次 → 两套 DNS → 结论可能不一致 → 日志说走 A、实际走了 B，
排查时完全没法看。所以 mihomo 那边只留 `MATCH,ferry`，判定全在本地代理。

## 五、演进史：六次尝试，五次错

记下来是因为**每次错的方式都不一样**，而且每次当时的逻辑都「看起来对」。

| 版本 | 做法 | 结果 | 错在哪 |
|---|---|---|---|
| 1.0.9~1.0.12 | 把节点写进用户的 Clash 配置（Verge Merge / CFW parsers / CFW config.yaml） | 全废，还留下后遗症 | CFW 有绿色版、各客户端路径不同、写错会毁人家的配置。**解决方案需要枚举用户装了什么，就说明绕路了** |
| 1.0.13 | 本地代理分流 + 域名本地解析成 IP 再传 | 可用，但 TUN 模式下失效 | 假设「本地能解析」——在 TUN 下不成立 |
| 1.0.16 | TUN 模式下**关闭**分流 | 境外全 502 | 注释写「TUN 自己的规则已经分好流了」，但那时规则是 `MATCH,ferry`（全走渡口）。**两处配合的逻辑，改一处没回头看另一处** |
| 1.0.21 | TUN 层加 `RULE-SET,cn` + 把 fake-ip 当国内 | 全网变慢（每个境外请求先撞一次超时） | 两条都错：fake-ip 不是地理信息；IP 规则在 fake-ip 下要额外解析 |
| 1.0.22 | 过滤 fake-ip 后重新问 223.5.5.5 | 仍然全错（域名反转误判） | **DNS 被 hijack，重新问也是 fake-ip**（约束 1） |
| **1.0.23** | 域名查后缀表，不碰 DNS | ✅ | — |
| 1.0.24 | 后缀表改哈希、日志按一级域名去重、补 CDN | ✅ | — |

**共同的错因**：每次都假设「我能拿到某个东西」（真实 IP / TUN 规则已经分流 /
配置文件路径固定），而**没有先验证这个假设在当前模式下成立**。

## 五之二、超时与失败记忆（1.0.25）

分流还有一个隐形成本：**判定对了，但那条路连不通**。

```
国内目标 → 走渡口 → 该目标从出口不可达 → 等超时 → 回退 Clash
```

统一 8 秒超时的时候，一个页面里只要有一个资源命中这种目标，页面就卡 8 秒；
而且每次重连都要再等一遍。这就是用户说的「偶发性的小卡顿」。

现在的策略：

| 机制 | 值 | 为什么 |
|---|---|---|
| 国内目标走渡口的超时 | **2.5 秒** | 国内 RTT < 100ms，2.5 秒不通基本就是不可达 |
| 境外走 Clash 的超时 | 8 秒 | 机场节点可能慢，需要耐心 |
| 失败记忆 | **5 分钟**（按 `host:port` + 方向） | 失败过的目标直接走另一条，不再重试 |
| `ResolveCn` | 三个 DNS **并发**，最坏 1.2 秒 | 原来串行等满三个是 3.6 秒 |

**为什么不并发竞速**：同时连两条、谁先通用谁，能彻底消除等待，但会
① 浪费上游（渡口按机器限速）② 同一站点随机选路，按 IP 绑定的登录态会错乱
③ 排查时说不清「这条为什么走了另一条」。

## 五之三、UDP 走哪条路（1.0.26）

TUN 里 UDP 和 TCP 是分开的两条出站，**不能共用同一个上游地址**：

| 出站 | 指向 | 为什么 |
|---|---|---|
| `ferry-tcp` | `127.0.0.1:<本地端口>` | 本地代理是 SOСKS5/HTTP 混合端口 |
| `ferry-udp` | **`127.0.0.1:<本地端口>`** | 远端 1080 **只监听 TCP**，UDP 必须走本地代理的 ASSOCIATE |

远端的 UDP 是「每条 TCP ASSOCIATE 临时开一个随机端口」，所以：

```
直发 10.13.24.1:1080 的 UDP  → ICMP port unreachable（全部丢包）
经本地代理 ASSOCIATE          → 拿到动态端口 → 正常
```

### 上游关联要共享（1.0.29）

SOCKS5 的 UDP ASSOCIATE 设计上就是**一个关联承载所有目标**（每条数据报自带
目标地址）。所以本地不要为每个客户端流各建一条上游连接：

```
别这么做：N 个客户端流 → N 条 TCP 控制连接 + N 个远端 UDP socket
应该这样做：N 个客户端流 → 1 条 TCP 控制连接 + 1 个远端 UDP socket
```

远端是单进程 async server，同时挂几十条控制连接时 accept 会忙，
新的 ASSOCIATE 超时 —— 症状是偶发「UDP 关联失败：上游不支持或连不上」。

回包分发用「最近 5 秒发过包的所有 relay 各发一份」：上游回来的包只有源地址，
不知道属于哪个客户端；SOCKS5 头里有目标地址，应用会自己过滤。

**还有一个坑**：共享的上游 UDP socket 必须绑 `IPAddress.Any`。
绑 `Loopback` 的话源地址是 127.0.0.1，发往远端的包出不去、回包也收不到，
表现是「关联建立成功、日志正常、但一个应答都没有」。

**这个错犯过两次**：`mihomo/mihomo-keeper.ps1` 修过一次（把 `$UdpHost`
改成 `127.0.0.1`），但客户端生成 TUN 配置的路径没跟着改。两处代码拼同一个
地址，改一处漏一处（见「两处配合的逻辑」那条元教训）。

症状很好认：界面显示「UDP / 游戏都走渡口」，但游戏延迟会突然飙到一百多
毫秒 —— 那不是线路慢，是 UDP 包全丢了在重传。

## 六、没有 Clash 的用户怎么办

检测不到本机代理（`DetectLocalProxy` 探测 7897/7890/7891/10808/10809/1080…）
时：`clashPort = 0`，全部走渡口。

此时境外网站打不开 —— **这是产品边界，不是 bug**。渡口不提供翻墙能力。
用户想翻墙就装自己的工具，渡口检测到会自动把境外交给它。

## 七、怎么验证（改完必须跑）

| 脚本 | 覆盖 |
|---|---|
| `tools/verify-domainsplit.cs` | 域名/IP/fake-ip 判定表，含后缀边界（`notbaidu.com`、`baidu.com.evil.com` 不能误命中） |
| `tools/verify-fakeip-split.cs` | fake-ip 不算国内、DNS 缓存生效、TUN 规则无 RULE-SET |
| `tools/verify-scenarios.cs` | 接管/节点模式 × 有无代理 × 代理挂掉，五种场景 |
| `tools/verify-lifecycle.cs` | 反复启停、Clash 开关、UDP、残局清理（22 项） |
| `tools/verify-tunconfig.cs` | 生成的 mihomo 配置结构 |

再加一道：**把生成的 `tun-config.yaml` 交给 mihomo 自己校验**

```powershell
mihomo.exe -t -f tun-config.yaml -d <配置目录>
# → configuration file ... test is successful
```

结构断言全过 ≠ mihomo 肯加载。这一步不能省。

## 八、如果要再加一种代理软件

1. 把它加进 `TunMode.cs` 的 `PROCESS-NAME` 例外列表（防环）
2. 确认它的本地端口在 `FerryCore.DetectLocalProxy` 的候选列表里
3. 不需要做任何「写它配置文件」的事 —— **永远不会**（踩坑 66）
