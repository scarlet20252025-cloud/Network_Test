# M5 · Android UDP 走隧道实测（2026-10-30）

> 目标：回答「hev `udp: 'udp'` 把 UDP 送进远端中继后，到底贵多少」，
> 以及一个更基本的问题 —— **它到底有没有在工作**。

## 结论先说

| 问题 | 实测结论 |
|---|---|
| 中继本身让 UDP 贵多少 | **p50 只差 +0.1 ~ +0.6 ms**（4 组重复测量，多次出现负数=噪声） |
| 手机的 UDP 有没有走隧道 | 关联**建起来了**，但**一个包都没转发**：10 条关联合计 `上行 0 B / 0 包` |
| 同机对照 | Windows 客户端同时段 `上行 640 B / 下行 640 B / 20 包` —— 中继侧正常 |

**所以 M5 的答案一开始不是「贵多少」，而是「手机上压根没通」。**
（已修，见下节「六、根因与修复」。修好后中继代价仍是亚毫秒级。）

## 一、中继的净成本：几乎为零

本机（Windows）跑同一个出口 `10.13.24.1:10820`，两条路径各 20 包：

```
直连               n=20  p50=4.4  p90=11.9  p99=18.2  max=18.2  丢 0
经中继 SOCKS UDP    n=20  p50=4.5  p90=6.8   p99=7.9   max=7.9   丢 0
                                → p50 +0.1 ms
```

重复 4 次（不同时刻）：

| 轮次 | 直连 p50 | 经中继 p50 | 差值 |
|---|---|---|---|
| 1 | 6.7 | 4.4 | **−2.3** |
| 2 | 4.1 | 4.6 | +0.5 |
| 3 | 4.9 | 4.8 | −0.2 |
| 4 | 5.2 | 5.0 | −0.2 |
| 5 | 4.4 | 4.5 | +0.1 |
| 6 | 5.5 | 6.1 | +0.6 |

差值在 ±2.3 ms 内来回摆，正负都出现 —— 说明**中继的额外延迟低于本机测量噪声**。
这和 Windows 端更早的结论一致（`tools/measure-udp-latency.cs`：隧道本身只贵 0.0 ms，
贵的是「本来能直连的流量被绕了一圈」）。

## 二、手机侧：关联建了，包没进去 ❌

中继日志里，同一次测量窗口内：

```
[16:07:06] UDP 关联关闭 10.141.59.235:65320  上行 320 B / 下行 320 B / 10 包   ← Windows 客户端
[16:01:23] UDP 关联关闭 10.141.57.9:50886    上行 0 B / 下行 0 B / 0 包       ← 手机
[16:01:27] UDP 关联关闭 10.141.57.9:50888    上行 0 B / 下行 0 B / 0 包       ← 手机
...（10 条手机关联，合计上行 0 B / 0 包）
```

hev 侧日志同时能看到关联建立：

```
[16:03:12] [I] 0xb400007ab906c490 socks5 client udp construct
[16:03:18] [I] 0xb400007ab906c3f0 socks5 client udp construct
[16:03:23] [I] 0xb400007ab906a0f0 socks5 client udp construct
```

`construct` 之后**没有任何错误、也没有任何后续** —— 包发出去就静默消失。
这和「服务端收到关联、但收到 0 个包」完全吻合，两层日志互相印证。

## 三、⚠ 测法本身踩的坑（比结论更值钱）

### 3.1 不能用 pcs 当 UDP 目标

第一版拿 `10.13.24.1:10820`（pcs 上的 UDP echo）当目标，结果手机发的包
在 echo 日志里源地址是 **`10.141.57.9`（手机自己的 wlan0）**，不是中继的
`10.13.24.1` —— 说明**根本没进隧道**，测到的是「直连有多快」。

原因在 `TunConfig.PUBLIC_V4`：隧道只收公网单播段，`10.0.0.0/8` 被显式排除
（这是对的 —— 打印机、路由器、远端 SOCKS5 自己都不该绕隧道）。
**UDP 打 10.13.24.1 == 打自己人，永不走隧道。**

→ 测隧道内 UDP，目标必须是公网地址（这里用 `223.5.5.5:53`）。

### 3.2 「有手机的关联行」不等于「包转发过」

第一版判定写的是「中继日志里出现手机 IP 的关联 → 确认走隧道」。
实测打脸：关联**会**出现，但 `上行 0 B / 0 包`。按旧判据会得出
「隧道 UDP 生效」的错误结论。

→ 判据必须细到**包数**：只有 `上行 N B / K 包` 里 N>0、K>0 才算转发过。

### 3.3 toybox 的 `nc -u` 不能用来量 RTT

| 试法 | 结果 |
|---|---|
| `nc -u -w 2` | `-w` 只管建连超时，UDP 无连接 → 不生效，进程挂住 |
| `nc -u -W 2` | `-W`（idle）实测也不退出 |
| `printf ... \| nc -u` | 同上，把 adb shell 拖死（30s 超时） |
| `timeout 3 nc -u ...` | 能退出，但量到的是「3 秒」，不是 RTT |
| `echo RC=$?` | toybox 下打印的是 `RC=True`（字符串，不是数字），不能判成败 |

→ 手机 RTT 不用 `nc` 量。中继代价用本机 SOCKS 路径测（同一出口、同一段链路），
手机侧只验「有没有真的转发」。

### 3.4 中继日志是 GBK，PowerShell 按「关联」匹配会一条都匹配不到

`run-relay.cmd` 里 `chcp 936 >nul`，日志是 **GBK** 写的。
用 PowerShell `Get-Content` 读进来再 `Select-String '关联'`，实测返回 0 条 ——
看起来像「没有 UDP 关联」，其实是编码问题（白跑一轮）。

→ 读它必须显式 `encoding='gbk'`（远端 python），或者直接 `iconv`。

## 六、根因与修复 ✅（2026-10-30 17:20 已验证）

### 根因：服务端返回 `BND.ADDR = 0.0.0.0`，hev 拿它去 `connect()`

`hev-socks5-tunnel` 在 `udp: 'udp'` 模式下，会用**服务端在 UDP ASSOCIATE
响应里给的 BND 地址**去 connect 自己的 UDP socket：

```c
// src/core/src/hev-socks5-client-udp.c
hev_socks5_client_udp_set_upstream_addr (HevSocks5Client *base, HevSocks5Addr *addr)
{
    ...
    res = hev_task_io_socket_connect (fd, sadp, sizeof (saddr), ...);
    ...
    HEV_SOCKS5 (self)->udp_associated = 1;
}
```

而 RFC 1928 允许服务端返回 `0.0.0.0:0`，含义是「客户端自己知道该往哪发」。
我们的 `ferry-socks5-server.py` 正是这么返回的（注释里写明了理由：服务端
不知道客户端眼里自己是什么地址，这本身**完全合规，不是 bug**）。

但 **Linux/Android 上 `connect()` 到 `0.0.0.0` 等价于「连本机」**。
于是 hev 把全部 UDP 载荷发进了手机自己的回环 —— 中继那边只看到
ASSOCIATE 握手成功（所以「关联行」会出现在日志里），却永远收不到包。
这完美解释了「关联建了 / 上行 0 B / 0 包」这个诡异组合。

### 修法：`udp-address`（官方为此提供的覆盖项）

`HevConfig.render()` 里补一行：

```yaml
socks5:
  address: 10.13.24.1
  port: 1080
  udp: 'udp'
  udp-address: 10.13.24.1     # ← 新增，值 = 服务端真实地址
```

README 对这一项的原话就是
**"Override the UDP address provided by the Socks5 server"** —— 正是这个用途。

### 验证（真机，2026-10-30 17:17~17:19）

| | 修复前 | 修复后 |
|---|---|---|
| 手机关联上行 | **0 B / 0 包**（10 条全 0） | **8204 B / 23 包**（9 条） |
| 手机关联下行 | 0 B | **最高 17184 B**（有真实回包） |
| 中继净成本 | — | p50 +1.6 ms（仍在噪声量级） |

单条示例：
```
10.141.57.9:50028  上行 4038 B  下行 17184 B  8 包   ← DNS 查询 + 真实应答
10.141.57.9:50035  上行 28 B    下行 0 B      1 包   ← 目标不回（预期）
```

### 教训

**「合规」不等于「能用」。** 服务端按 RFC 返回 `0.0.0.0` 是对的，
客户端库按 RFC 接受它也是对的，但两者组合在 Linux/Android 上就是不通 ——
因为 `connect(0.0.0.0)` 的语义是平台相关的一层隐含约定，不在协议里。
这类「双方各自正确、合起来错误」的问题，只能靠**端到端实测**发现，
而且必须有「包数」这种细粒度的判据 —— 只看「关联已建立」会漏掉它。

## 四、下一步（UDP 已通，这些是原先怀疑的方向，留作记录）

1. **定位 hev 为什么构造了 UDP 会话却不发包**。
   已知：`socks5 client udp construct` 之后无任何日志、无错误。
   可疑方向：hev 的 UDP 发送依赖 `sendmmsg/recvmmsg`（`hev_socks5_session_udp_gms`），
   而 `gso_size` 在 Android 内核上可能不被支持 → 查 `hev_socks5_udp_recvmmsg` 的返回值。
   注意 hev 的 log-level 现在是 `info`，调到 `debug` 会打出
   `socks5 session udp fwd b recv` 这类细节。
2. **考虑回退到 `udp: 'tcp'`**（UDP over TCP，RFC1928 之外但 hev 支持），
   代价是队头阻塞，但至少能用。要先验。
3. 修好之后，`tools/measure-android-udp.py` 里的判据（看包数）
   会自动给出 PASS/FAIL，不需要改工具。

## 五、复现方法

```bash
# 1. pcs 上起 UDP echo（可选，本测法其实不需要它）
powershell -File tools/start-udp-echo.ps1

# 2. 手机连上并起隧道（App 里点「开始借网」）
# 3. 跑测量
python tools/measure-android-udp.py --rounds 4
```

判据看输出第三段「按来源看包有没有真的转发」。
